Every CTO leading an [AI transformation](/blog/how-to-start-ai-transformation) eventually hits the same architectural fork in the road. Two senior engineers build a promising internal Slack bot over a long weekend using a Python agent SDK and a few API keys. It triages support tickets or summarizes pull requests well enough that product, marketing, finance, and operations immediately ask for fifteen more agents connected to their own tools.

At that moment, leadership faces the **internal AI agent platform build vs. buy** decision:

1. **Build in-house:** Assign a platform team to turn that weekend prototype into a multi-tenant internal agent runtime with sandboxes, OAuth vaults, approval gates, and a web UI.
2. **Buy closed SaaS:** Roll out a proprietary per-seat workspace like [Dust](https://dust.tt) or [Glean](https://www.glean.com) across the company.
3. **Adopt the open-source middle ground:** Run an [open-source AI coworker platform](https://agenta.ai) for the undifferentiated runtime and governance layers while owning your company knowledge, skills, and infrastructure.

Enterprise data shows how quickly teams are reconsidering pure custom builds. According to [Menlo Ventures' State of Generative AI in the Enterprise report](https://menlovc.com/perspective/2025-the-state-of-generative-ai-in-the-enterprise/), the share of enterprise AI solutions built entirely in-house dropped from **47% in 2024 to 24% in 2025**, while **76% of organizations** shifted to buying or adopting existing platform layers so their engineers could focus on domain-specific workflows.

This guide breaks down what a production internal AI agent platform actually requires under the hood, models the three-year total cost of ownership (TCO) for a 100-person organization across all four architectural paths, and gives CTOs a concrete decision matrix for choosing what to adopt and what to own.

## Why the "weekend agent prototype" is a trap for engineering teams

When strong engineers look at an agent loop, their first instinct is almost always to build it themselves. Calling an LLM with tool definitions in Python takes fewer than a hundred lines of code. If the goal is a single script run by one developer on their local laptop, a custom script is enough.

The trap springs when that script has to become an **internal AI agent platform** used safely by fifty or five hundred employees across engineering, product, operations, sales, and support.

In [Ramp Engineering's breakdown of building their internal background coding agent](https://builders.ramp.com/post/Why-we-built-our-background-agent), the team documented that the LLM prompt loop was a tiny fraction of the system. To run agents reliably in production, Ramp had to engineer **15 distinct harness and infrastructure subsystems**, including:

- Ephemeral VM and container sandbox images with pre-warmed caches
- Per-session network egress proxies and credential injection so agents never see raw secrets
- Multiplayer session state so multiple teammates can join the same agent run from Slack, web, or Chrome extensions
- Durable background execution queues, webhook routers, and crash recovery
- Human-in-the-loop permission gates for destructive or external actions

As [O'Reilly Radar's analysis on building your own agent platform](https://www.oreilly.com/radar/the-case-against-building-your-own-agent-platform/) notes, teams that build monolithic agent infrastructure from scratch spend 6 to 18 months maintaining plumbing while frontier models, tool protocols like the Model Context Protocol (MCP), and computer-use harnesses shift underneath them every quarter.

### The 7 subsystems your team actually has to build and maintain

Before greenlighting an in-house platform build, walk your architecture team through the seven layers required to move beyond a developer-only script:

1. **Isolated compute and headless browser sandboxes:** Every agent run that writes files, executes Python or Node scripts, runs `git` and `gh`, or inspects web pages needs an isolated Linux container and headless Chromium browser (such as a [Daytona](https://www.daytona.io) sandbox). Running untrusted tool outputs on shared worker nodes is a critical security failure.
2. **Multi-harness execution and credential routing:** Frontier agent capabilities now depend heavily on the execution harness, not just the raw model API. Supporting [Claude Code](https://code.claude.com/docs/en/overview), [Codex](https://developers.openai.com/codex), and [Pi](https://pi.dev) while decoupling the harness from the model and the credential source requires a clean boundary between `Application -> Agent Workflow Service -> Runner -> Harness -> Sandbox`.
3. **Shared persistent knowledge vs. temporary session scratchpads:** An internal coworker needs a [company AI brain](/blog/how-to-build-a-company-ai-brain) that survives across sessions. If you only build stateless RAG, agents forget every correction the moment a chat ends. You need persistent shared agent files (`AI Drive`) for durable team context alongside temporary session files for scratch work.
4. **Encrypted OAuth vault and 1,000+ tool integrations:** Connecting Slack, GitHub, Notion, Linear, HubSpot, Google Workspace, and internal databases requires OAuth token refresh loops, per-workspace scoping, and MCP server lifecycle management.
5. **Action-level human approval gates (`Allow`, `Ask`, `Deny`):** Reading a Linear ticket or searching a codebase should run automatically (`Allow`). Sending an external customer email, posting to a company Slack channel, or deleting a schedule must pause execution and render an interactive approval card (`Ask`) or block outright on policy (`Deny`).
6. **Durable cron schedules and webhook event subscriptions:** Autonomous coworkers do most of their valuable work when no human is typing in a chat box. That requires a five-field UTC cron scheduler and an event subscription engine with payload mapping, version pinning, and delivery logs.
7. **Plain-language builder UX and multi-surface deployment:** If updating an agent's instructions or skills requires a pull request and a container redeploy, 80% of your company cannot build or improve coworkers. Your platform team becomes a permanent ticket queue for every prompt tweak requested by marketing, ops, or support.

## Why buying closed per-seat SaaS creates a different problem

Recognizing the hidden engineering cost of building those seven layers, many CTOs swing to the opposite extreme and buy a closed SaaS workspace like Dust or Glean.

While closed SaaS gets a pilot running in a week, it introduces three structural problems as adoption scales across the organization:

- **The compounding per-seat tax:** Closed SaaS vendors price like traditional seat-based productivity suites. At **$29 per user per month** (Dust) or **$50+ per user per month** (Glean), rolling out internal agents to 100 employees costs **$34,800 to $60,000+ every year** before a single complex background automation runs. At 300 employees, you are paying six figures annually just so occasional viewers can read an agent's output or click an approval button.
- **Company knowledge trapped in a vendor cloud:** Every plain-language instruction, reusable skill, research synthesis, and decision log your team creates inside a closed SaaS tool is stored in a proprietary schema on the vendor's servers. If you ever switch tools or need to run workloads inside an air-gapped VPC, your operational company brain cannot be exported as a clean folder of files and container images.
- **Locked into a single proprietary harness and credit markup:** Closed platforms wrap model calls in their own proprietary orchestration loop and credit tiers. You cannot choose between specialized coding and computer-use harnesses like [Claude Code](https://code.claude.com/docs/en/overview), [Codex](https://developers.openai.com/codex), or [Pi](https://pi.dev), nor can your engineers attach their existing Claude Pro/Max or ChatGPT subscriptions.

## The CTO decision framework: What to adopt vs. what to build internally

The smartest engineering organizations in 2026 treat an internal AI agent platform the same way they treat Kubernetes, Postgres, or CI/CD: **never build undifferentiated runtime plumbing from scratch, and never rent a closed black box that taxes every employee seat.**

Use this two-part architectural rule to allocate your engineering budget:

### Layer 1: Adopt an open-source foundation for runtime plumbing

Use an MIT-licensed platform like [Agenta](https://agenta.ai) out of the box for:

- **Container and browser sandboxing:** Let Agenta and Daytona manage per-session Linux containers, headless Chromium, and filesystem boundaries.
- **Harness and model abstraction:** Run [Claude Code](https://code.claude.com/docs/en/overview), [Codex](https://developers.openai.com/codex), and [Pi](https://pi.dev) with your own API keys or existing Claude Pro/Max and ChatGPT subscriptions without rewriting orchestration code when a new model drops.
- **Governance, schedules, and approval cards:** Use built-in `Allow / Ask / Deny` tool permissions, encrypted credential storage, cron schedules, and webhook subscriptions.
- **Multi-surface delivery:** Publish coworkers to Slack, Telegram, WhatsApp, an [embeddable web chat widget](https://agenta.ai/docs/guides/embed-an-agent), and REST APIs with zero custom bot boilerplate.

### Layer 2: Build and own your company-specific intelligence

Focus 100% of your internal engineering and operator time on the assets that actually differentiate your business:

- **Persistent shared agent files (`AI Drive`):** Curate your product architecture docs, customer ICP definitions, operational playbooks, and decision logs inside a shared durable folder structure that compounds across every run.
- **Reusable domain skills and plain-language instructions:** Empower domain leads in engineering, ops, marketing, finance, and support to encode their best workflows into versioned skills.
- **Proprietary internal MCP servers and APIs:** Have your engineers expose internal billing, telemetry, or warehouse tools as clean MCP endpoints or CLI scripts that any governed coworker in Agenta can call safely.

### Quick checklist: Which path fits your organization?

- **Choose the open-source middle ground ([Agenta](https://agenta.ai))** if you want same-day deployment (self-hosted via Docker/Helm under the MIT license or on Agenta Cloud starting at $29/month with unlimited seats), isolated Linux/browser sandboxes, multi-harness support (`Claude Code`, `Codex`, `Pi`), a shared persistent `AI Drive`, and plain-language coworker building for every department.
- **Choose a developer code framework ([LangGraph](https://www.langchain.com/langgraph) + [Temporal](https://temporal.io))** only if you are embedding a custom, code-only state machine inside your external commercial software product and have dedicated engineers to build the surrounding application UI.
- **Choose a closed per-seat SaaS tool ([Dust](https://dust.tt) or [Glean](https://www.glean.com))** only if you have zero engineering capacity to run a container or manage API keys, do not need full Linux/browser sandboxes, and are comfortable paying $35,000 to $180,000+ over three years in per-seat licensing.
