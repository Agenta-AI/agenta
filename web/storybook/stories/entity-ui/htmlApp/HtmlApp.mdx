# Agent HTML apps — Run mode

An HTML file in an app folder of an agent drive **runs**: the file's folder becomes the
app dir, the page renders in a sandboxed iframe (no `allow-same-origin`), and it reaches its own
files through `window.agenta.fs`, a `MessagePort` the host hands it on load. The contract lives in
`@agenta/entities/drive` (`protocol.ts`, `manifest.ts`, `mockHost.ts`); these stories run on
`createMockHtmlAppHost`, the behavioural reference lane A's real host must match.

In the Files pane an app opens running with no file access; the file's ⋯ menu switches to its code
and back, and "File access…" shows and changes the stored level. The app's first read asks "read
files?", its first write asks "change files?". Answers are kept per signed-in user, mount and
folder in localStorage, survive reloads and tabs, and apply to the running app.

## Pieces

| Piece                 | What it does                                                                                                                                                                                                                              |
| --------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `assembleRunDocument` | Run: same-mount CSS + images inlined, author scripts kept (same-folder `<script src>` inlined, external dropped with a note), then CSP meta → `#agenta-tokens` → `#agenta-kit` → bridge stub prepended to `<head>`. No interceptor: nav rides the port. |
| `HtmlAppBody`         | The running app. It starts with the stored answer or no access; a call that needs more asks about what it tried. The env context injects host factory, mount io, kit CSS, token resolver, grant store.                             |
| `GrantSheet`          | `AccessQuestion` — "Let _name_ read / change files in _dir_?", Allow / Don't allow — and `GrantSheet`, the ⋯ "File access…" setting: Read / Read and write / None, write only where the drive's upload gate allows edits.             |
| `RunView`             | The iframe; its controls (‹ back, "Files changed" pill, error badge → list → Copy, Refresh) portal into the file toolbar. Attaches the host on load, detaches on unmount, pushes theme tokens on theme change.                    |
| `useAppManifest`      | Reads `<dir>/app.json` (absent → defaults: `read`, `index.html`, kit on).                                                                                                                                                                 |
| `useChangedHint`      | Diffs the app dir's listing query (etag → mtime → size) on refetches not caused by the app's own write and calls `host.notifyChanged`; `onWrite` bumps the listing through `refreshMountListing`.                                         |

## What runs for real

The Run document carries the real `BRIDGE_STUB` and `KIT_CSS`, so the app in the iframe talks to
the host over the port exactly as it does in the drive. Stories swap only the host: `HtmlAppEnv.createHost`
injects `createMockHtmlAppHost` in place of `createHtmlAppHost`, and `io` serves the mock's files.
The RunView driver buttons send what the stub would (`host.handle(FsRequest)`, a nav href, a
script error) so each state is one click away.

Every story renders under the Theme toolbar in light and dark: the controls use semantic token
classes, and the app document receives the kit tokens resolved from the root's `--ag-*` variables.
There is no `AntdVsAgenta` pair — these components have no antd predecessor.
