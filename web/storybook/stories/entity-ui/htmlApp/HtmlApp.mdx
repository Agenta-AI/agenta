# Agent HTML apps — Run mode

An HTML file in an agent drive can be **run**, not just previewed: the file's folder becomes the
app dir, the page renders in a sandboxed iframe (no `allow-same-origin`), and it reaches its own
files through `window.agenta.fs`, a `MessagePort` the host hands it on load. The contract lives in
`@agenta/entities/drive` (`protocol.ts`, `manifest.ts`, `mockHost.ts`); these stories run on
`createMockHtmlAppHost`, the behavioural reference lane A's real host must match.

Everything here is behind `userScopedFlagAtom("agent-apps")`. Flag off, the viewer is byte-for-byte
the Preview | Source it was (locked by `tests/unit/htmlApp.assemble.test.ts`).

## Pieces

| Piece                 | What it does                                                                                                                                                                                                                              |
| --------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `assemblePreview`     | Today's Preview: inline same-mount CSS + images, strip every script vector, add the nav interceptor.                                                                                                                                      |
| `assembleRunDocument` | Run: the same inlining, author scripts kept (same-folder `<script src>` inlined, external dropped with a note), then CSP meta → `#agenta-tokens` → `#agenta-kit` → bridge stub prepended to `<head>`. No interceptor: nav rides the port. |
| `HtmlAppBody`         | Preview \| Source \| Run. Run needs a drive and a grant; the env context injects host factory, mount io, kit CSS, token resolver, grant store.                                                                                            |
| `GrantSheet`          | "Run _name_?" — Read files / Read and write files, preselected from `app.json`'s `access`; the write option only where the drive's upload gate allows edits. A hidden third section is reserved.                                          |
| `RunView`             | The iframe + status strip: dot, `Running · read + write · dir`, ‹ back, Refresh ▾ (Reload files), "Files changed" pill, error badge → list → Copy. Attaches the host on load, detaches on unmount, pushes theme tokens on theme change.   |
| `useAppManifest`      | Reads `<dir>/app.json` (absent → defaults: `read`, `index.html`, kit on).                                                                                                                                                                 |
| `useChangedHint`      | Diffs the app dir's listing query (etag → mtime → size) on refetches not caused by the app's own write and calls `host.notifyChanged`; `onWrite` bumps the listing through `refreshMountListing`.                                         |

## What is a placeholder

Lane A's bridge stub has not landed in this branch. The Run document carries
`PLACEHOLDER_BRIDGE_STUB` (`assemble.ts`, marked `TODO(lane A)`): it defines `window.agenta` with a
`ready` that rejects (`code: "unavailable"`), so a starter written against the contract shows its
own "bridge unavailable" state instead of throwing on an undefined global. The iframe therefore
cannot itself call `fs` yet; each RunView story's driver buttons send exactly what the stub would
(`host.handle(FsRequest)`, a nav href, a script error) and the strip reacts as it will in the drive.
The default host in `HtmlAppBody` is the in-memory mock (`defaultCreateHost`, also `TODO(lane A)`);
the kit CSS is a story stand-in until lane E's file is injected through `HtmlAppEnv.kitCss`.

Every story renders under the Theme toolbar in light and dark: the strip uses semantic token
classes, and the app document receives the kit tokens resolved from the root's `--ag-*` variables.
There is no `AntdVsAgenta` pair — these components have no antd predecessor.
