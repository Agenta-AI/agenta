**Nothing purges sessions, turns, interactions or mounts.**

There is also no query that deletes rows by `deleted_at` age anywhere in `api/oss/src` or `api/ee/src`.
- The OSS cron jobs are `api/oss/src/crons/{gateways,queries,triggers}.txt`. They only call the OAuth-attempt sweep, evaluation-run refresh and trigger-schedule refresh. None of them touches sessions or mounts.
- Archiving is soft and reversible. It sets `deleted_at` on the stream row and the session's mounts (`api/oss/src/core/sessions/service.py:369-400`, `api/oss/src/core/mounts/service.py:981-1029`). Nothing ever purges archived items later.

## 2. Deletion

There are three different "delete" operations.

| Operation | Endpoint | Effect |
|---|---|---|
| Delete session | **`DELETE /sessions/?session_id=&lt;id&gt;`** (operation `delete_session`, permission `EDIT_SESSIONS`) | **Hard delete, including the mount storage** |
| Archive session | `POST /sessions/archive`, reversed by `POST /sessions/unarchive` | Soft (`deleted_at`) on the stream row and the mounts. Files are untouched |
| Kill session | `DELETE /sessions/streams/?session_id=&lt;id&gt;` (operation `delete_session_stream`, permission `RUN_SESSIONS`) | Tears down the sandbox, cancels pending interactions, and soft-deletes the stream row. Mounts and files are untouched |

The delete and archive routes are at `api/oss/src/apis/fastapi/sessions/router.py:2117-2160`, and the delete handler is at `:2408-2430`. The kill route is at `router.py:445-450`, its handler at `:630-660`, and the soft delete at `streams/service.py:415-430`.

**What hard delete does.** `SessionsService.delete_session` (`api/oss/src/core/sessions/service.py:336-367`) runs these steps:
1. Hard-deletes `session_turns` (`turns/dao.py:331-339`, `sa_delete`).
2. Hard-deletes `session_interactions` (`interactions/dao.py:281-290`).
3. Calls `mounts_service.delete_session_mounts` (`api/oss/src/core/mounts/service.py:958-979`). This:
   - hard-deletes every mount row with that `session_id` (`dbs/postgres/mounts/dao.py:237-262`);
   - then calls `delete_prefix` on `[&lt;namespace&gt;/]mounts/&lt;project_id&gt;/&lt;mount_id&gt;/` for each mount (prefix built at `service.py:447-460`).
   - This covers the `__ag__session__&lt;uuid5&gt;__cwd` mount, including `.codex/sessions` and `agents/sessions`, and the attachments mount.
4. Hard-deletes the stream row (`streams/service.py:1134-1149`).

**What hard delete leaves behind.**
- Records are deliberately kept (`service.py:350`).
- `session_inputs`, `session_commands`, `session_executions` and `session_attachments` rows are not touched by this fan-out.

**Caveats on purging the files.**
- `delete_prefix` (`api/oss/src/core/store/storage.py:742-751`) lists the current keys and calls `remove_objects` without version IDs (`delete_keys` at `:723-740`). On the versioned bundled SeaweedFS, this only writes delete markers. The file contents stay as noncurrent versions until the 30-day lifecycle rule expires them, and only if SeaweedFS enforces that rule.
- On a remote S3 bucket where the operator turned versioning on, the contents stay until the operator's own lifecycle policy removes them.
- So the files are not purged immediately.
- Storage deletion is skipped silently if `mounts_store` or `bucket` is not configured (`mounts/service.py:972`).

**Admin path.** There is no admin endpoint that hard-deletes a session or purges mount storage. The only `/admin` routes are billing, spans, events, records, triggers, gateways, evaluations and accounts (`api/ee/src/main.py:148-169`, `api/entrypoints/routers.py:1988`, `:2025`, `:2039`, `:2115`).
- `delete_prefix` has exactly one caller, `delete_session_mounts`.
- Deleting a project cascades the `mounts` rows through a foreign key (`dbs/postgres/mounts/dbes.py:17-21`). It does not delete the objects under `mounts/&lt;project_id&gt;/`, so those are left orphaned.

**Bottom line:**
- **Kept forever?** Yes: session rows, turns, harness logs and cwd mount files stay until the user deletes the session. Archiving and killing do not remove them.
- **Exceptions:** EE cloud plans prune records after 7, 31 or 92 days. The bundled SeaweedFS expires noncurrent object versions after 30 days by default.
- **Hard delete with storage:** `DELETE /sessions/?session_id=` is the only path. It removes the rows and the current objects, but on versioned storage the old versions remain until the lifecycle rule expires them.</result>
