Agent apps, one page

An agent writes a small HTML app into its session's drive. The user runs it beside the conversation. The app reads and writes files in its own folder through a narrow bridge, and the agent reads those same files on its next turn. Everything below is the plan for making that loop real, consistent, and safe.

What an App is

A folder of files the agent wrote, opened as a program

An App is an ordinary HTML file that the agent wrote into the session's drive, plus the data files beside it, opened in a mode where its own JavaScript is allowed to run. Nothing is uploaded, deployed or hosted. The file sits next to the agent's other files; the "app" is what the user sees when Agenta executes it beside the conversation instead of showing it as a static page.

A folder is an app because it contains an app.json manifest. Not a file extension, not a guess from the HTML. The explorer shows such a folder as an App tile with an Open action; the Run tab reads the manifest to know the entry file and the access to ask for; the agent reads it on later turns to recognize what it already built.

Three ways to open an HTML file
  • Preview, the default. Scripts stripped. Safe and inert, exactly as today.
  • Source. The code.
  • Run. Executes the file in the same sandboxed iframe and injects window.agenta, a bridge with eight file methods scoped to the app's folder. The user chooses Run and picks read or read-and-write.
The running example

The agent writes apps/launch-board/index.html and board.json. The user drags a card; the app saves the new layout to board.json. Next turn the agent reads that file and sees what the user did. Files are the shared state; the App is a UI the agent made for editing them.

One folder per app
apps/launch-board/
  app.json      the manifest: this folder is an app
  index.html    the entry, starter copy or custom
  config.json   title, columns; agent writes
  board.json    data; app writes, agent reads
What the app can and cannot do
  • Can: read, write, list, stat and remove files in its own folder; draw anything, DOM or canvas; know when the folder changed and when its tab is hidden.
  • Cannot: reach the network, call any API, see a token, touch another folder, read the transcript, send a message, or store anything outside its files.
  • Everything it cannot do, the agent does for it by writing a file.
Six shapes it covers
  • Board, checklist, sheet, form: edit structured state beside the chat.
  • Review queue: many files, decisions in one JSON.
  • Dashboard: read-only view of data the agent produces on a schedule.
  • Wizard: structured input the agent needs, handed back via a composer draft.
  • Whiteboard and charts: canvas, same bridge, merge-by-id data.
  • Team tools: the one shape that lives with the agent, not a session.

How an App gets created

Only one way in: an agent, during a turn, using its file tools. There is no app builder and no upload path. The user asks for something; the agent decides it is an app; a folder appears with a file card in the reply. What keeps two sessions from producing two different "boards" is that the agent does not write the common apps at all.

How the agent knows any of this

One first-party skill, agenta-apps, attached by default to any agent with a drive and detachable. It carries the folder shape, the bridge contract, the starter catalogue, the custom-app rules, and the agent-level rules: check the registry before creating, write one registry file per session, add a note when feedback repeats.

Starters

Real HTML files in a platform bundle, versioned as board@1, copied server-side so no tokens are spent and nothing drifts. Board ships first; checklist, review-queue, form, sheet and dashboard follow, then whiteboard, chart and diagram on canvas. An agent can later promote a settled custom app into its own starter, on the user's word, with data stripped.

The iteration loop

The agent cannot run the app; it has no browser. The Run tab relays bridge rejections and script errors, and one click drafts them into the composer so the agent can fix a folder name it never saw. The grant is keyed by folder, so the agent's edits during creation never re-prompt the user.

Session level

The app instance: its folder, its data, its grant. One per conversation. Where almost every app lives.

Agent level

What every session should find the same: the skill, starters, schedules and tool connections in the Build panel, and agent-files/.apps/ with a registry, notes and kit overrides. Team tools that must outlive a session go in agent-files/apps/, off by default.

The placement question

"Would a second session asking the same thing need this?" Yes: agent level. No: session level. Data is always session level, except for team tools.

The loop and the boundary

What makes it safe
  • The iframe holds no cookie, token or HTTP client. It can only message the page that contains it.
  • It has no way out: default-src 'none' stops fetch and beacons, and dropping allow-popups stops window.open, which no CSP directive governs. Verified, not assumed.
  • The frontend forwards eight file operations, nothing else, only inside the app's folder, only under a grant the user chose.
  • The server bounds the mount: permission, project, no ... The folder is bounded too, by a prefix-scoped token the API checks on every call — it was a frontend guardrail until three egress holes showed that enumerating exits is not a security model.
  • Preview is a different document: it keeps allow-popups for ordinary external links and has no bridge, so it carries its own policy. Stripping scripts was not enough — a data: iframe ran one anyway.
What makes it consistent
  • Common apps are copied from versioned starters by a platform op, not generated. Two sessions get the same bytes.
  • Custom apps are built on an injected design kit with the host's theme tokens.
  • A folder is an app because of an app.json manifest. One folder per app, data as sibling JSON, one writer per file.
What makes it stick
  • The agent learns all of it from one first-party skill, agenta-apps, attached to agents with a drive.
  • The agent's own folder, agent-files/.apps/, records what it built and can hold promoted starters.
  • Errors inside the iframe are relayed to the Run tab and, on the user's click, into the composer.

Decisions taken

  • Ship read and write together, behind one grant prompt. Read-only is a grant level, not a release.
  • Name window.agenta, versioned; error codes frozen.
  • MessageChannel port, not postMessage("*").
  • Sandbox allow-scripts allow-forms; CSP blocks external scripts; workers and WASM only per shelf entry.
  • Server bounds the mount and the folder. The folder was a frontend guardrail until two egress holes showed that enumerating exits is not a security model; it is now a prefix-scoped token the API checks on every file call.
  • Grant keyed by folder and level, survives edits, per browser session.
  • Conflict detection in phase 1: ETag on reads, If-Match on writes, automatic in the stub. Agent tools stay unconditional; skill says read-before-write.
  • Caps 4 MB read, 1 MB write.
  • Workspace v1: pane B holds non-session tabs only. Two panes is the limit. No Dockview.
  • Package-first: both hosts mount the same workspace; /m is the target app.
  • Close a running session tab still stops it, until a session can have two views.
  • Explorer tabs pin to a drive; follow-focus is a later toggle.
  • Apps are created by the agent only. No upload story.
  • A folder is an app because of app.json. No heuristics on HTML.
  • Starters copied by a platform op, board first; five more plus three canvas starters in phase 3.
  • agenta-apps skill auto-attached to agents with a drive; detachable.
  • Design kit: tokens plus a house style under 6 KB; per-agent overrides tokens-only, on request.
  • Agent layout under agent-files/.apps/, dimmed like .tools/; registry and notes as folders, one writer per file; one mount, not two.
  • Cross-session apps off by default; scheduled apps live at agent level.
  • Refresh: change hint and stat in phase 1; "Ask agent" and schedule readout in v1.1; proxied read-only tool calls designed only; model calls planning only.
  • Library shelf, seven entries, one heavy, inlined at assembly; no CDN.
  • Agent-owned starters: explore after phase 3, skill-backed, user-initiated, data stripped.

Still open

  • Whether agent-files/ travels when an agent is duplicated, and what happens to the agent mount on delete. Platform decisions outside apps; the skill copes either way.
  • Whether the bundled store's native conditional put is available, or the service falls back to stat-compare-put. Decided at implementation, documented either way.
  • Performance budgets for two streaming sessions plus an app iframe. Measured in 2.6 before phase 4 is scheduled.
  • Agent-file history: SeaweedFS versioning exists with retention; exposing list-versions and restore is "when it bites".
