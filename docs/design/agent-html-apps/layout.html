Agenta · agent HTML apps · agent-level layout

What lives with the agent, so every session finds it

A session holds an app. The agent holds everything that makes the next session's app the same one: starters, a record of what was built, notes, a place for apps that outlive a conversation, and the configuration that feeds them. This page specifies that layer file by file and setting by setting. Companion to Agent App Creation, the plan, the walkthrough and the field test.

What is already true

The layout builds on things the platform does today. Each of these was checked in the code, and the design leans on them rather than adding new mechanisms.

One durable mount per agentEvery agent artifact gets a mount, created on first use, keyed by artifact id and a name that defaults to default. It is shared by all of that agent's sessions and runs.
mounts/service.py · get_or_create_agent_mount
Mounted as agent-files/The runner symlinks that mount into the sandbox working directory as agent-files/. The agent's instructions already say it is durable and survives sessions.
platform_instructions.py · Files and storage
Hidden infrastructure precedentagent-files/.tools/ holds the agent's own binaries; .tools/bin/ is copied into the working directory before each session and setup.sh runs with a two-minute limit.
platform_instructions.py · Installing tools
Dot folders are dimmed, not hiddenThe Files pane greys out dot-prefixed paths like a file browser does. Only .agenta-* segments and the agents/ folder are hidden outright as runner plumbing.
driveTree.ts · isHiddenPath · isInternalDrivePath
Agent files fold into the session viewThe Files pane shows both mounts in one tree, with the agent mount under agent-files/ and an origin tag on each row when a listing mixes the two.
useSessionDrive.ts · fileOrigin · driveHasMixedOrigins
Credentials are prefix-scopedThe sandbox gets short-lived credentials scoped to one mount's prefix. A session cannot reach another agent's mount.
mounts/service.py · sign_mount_credentials
Schedules existTriggers include cron schedules: a five-field expression in UTC on a one-minute floor, bound to a workflow revision. A scheduled run is an ordinary agent turn with no browser attached.

The two levels

An app instance is session-level: its folder, its data, its grant. Everything that should be identical across sessions is agent-level. The rule for placing something is one question: if a second session asked the same thing, would it need this? If yes, it is agent-level.

The durable folder, file by file

Everything under agent-files/.apps/ is the agent's app infrastructure. It follows .tools/: dot-prefixed so the Files pane dims it, durable, created by the agent on first use, never provisioned by the platform. The visible agent-files/apps/ holds only apps that must outlive a session.

Why folders, not single files, for registry and notes. Several sessions of the same agent can run at once, and the agent's writes through the mount are unconditional. A single registry.json would be a two-writer file with no conflict detection. One file per session, and one file per note, is the same rule the field test gave apps: one writer per file. The reader lists the folder; listing is cheap.

Dimmed is not hidden. Users will see .apps/ greyed out in the agent-files tree, and can open it. That is acceptable and arguably right: starters and notes are the user's to inspect. If a truly hidden folder is wanted, the platform's hidden prefix is .agenta-, so the alternative name is .agenta-apps/. Recommendation: .apps/, dimmed, consistent with .tools/.

Schemas

.apps/registry/<session-id>.json
{
  "version": 1,
  "session_id": "s_41",
  "apps": [
    {
      "slug": "launch-board",
      "path": "apps/launch-board",
      "template": "board@1",          // or "agent:retro-board@2", or null for custom
      "created_at": "2026-09-17T19:02:11Z",
      "updated_at": "2026-09-17T21:48:03Z",
      "state": "active",              // active · archived · missing
      "notes": "user asked for WIP limits"
    }
  ]
}

The agent rewrites its own session's file whole after each app event. Another session reads all files under registry/ and merges by slug.

.apps/kit/brand.json
{
  "version": 1,
  "name": "Acme Support",
  "accent": "#1D4ED8",          // one colour; the kit derives soft and ink variants
  "logo": null                  // v2: a data URI, inlined by the assembler
}

The assembler maps accent onto --ag-accent and derived tokens. Nothing else in the kit is overridable from this file.

.apps/kit/overrides.css · rules
/* Allowed: token redefinitions and .ag-* additions */
:root { --ag-radius: 4px; }
.ag-btn-primary { letter-spacing: .02em; }

/* Rejected by the assembler: */
/*  @import, url() to http(s), @font-face with     */
/*  remote src, anything outside :root and .ag-*   */

The assembler parses this file and drops disallowed rules with a note in the Run tab's error strip. CSS cannot execute code, but it can exfiltrate through url(); the CSP's img-src is the second line.

.apps/notes/<date>-<slug>.md
# 2026-09-18 · board · WIP limits
Second session in a week where the user asked
for a per-column limit on a board. Consider
adding `wip_limit` to board config, or promoting
the session-B variant.
Sessions: s_41, s_58
.apps/layout.json
{ "version": 1, "created_at": "2026-09-17T19:02:11Z" }

If the skill ever renames a folder or changes the registry shape, it checks this first and migrates once. Without it, every future change is a guess about what an old agent has.

One mount or two

Agent mounts are named, and nothing uses a second name yet. That opens a choice: keep app infrastructure inside the default mount under .apps/, or give apps their own mount, say apps, with its own prefix and credentials.

A · inside default, under .apps/B · a second named mount apps
Sandbox pathagent-files/.apps/; nothing new for the runnerA second symlink, say agent-apps/; runner change, instructions change
Files paneFolds into the existing agent-files tree, dimmedA third origin; the drive UI would need a new tag and filter
CredentialsSame prefix-scoped token the agent already getsA second token per session; separately revocable
Visibility controlSame as agent-files: project members who can see the agentCould be permissioned separately, for example promote requires a role
CostOne paragraph in the instructionsRunner, API defaults, drive UI, instructions
When it pays offNowIf starters become a shared, permissioned asset across agents, or if agent-files quota needs to exclude apps

Recommendation: A. The named-mount lever exists and is worth knowing about, but nothing in v1 needs a separate prefix. Skill-backed starters already give cross-agent sharing through the registry, which is the case that would otherwise justify B.

The one thing to say out loud. Anything the agent writes under agent-files/ is visible to every project member who can see the agent, and anything under apps/ there is runnable by them. Promotion and cross-session apps are publishing actions inside the project. The skill's confirmation text says so.

What the user sees

Two surfaces today, one later. The Files pane already shows the agent mount folded under agent-files/; it needs only to recognize app folders. The Skills page already lists skills; it needs a preview for the starter kind. The Build panel section is the later one.

Setup by app type

For each app type: what must exist at the agent level before the first session can succeed, what the session ends up with, and who does each step. Level markers: agent is agent-level, session is session-level, platform ships with Agenta.

Board · checklist · sheet · form

The common case. Needs nothing beyond the skill.
  • 1platformStarter in the bundle: board@1, checklist@1, sheet@1, form@1
  • 2agentagenta-apps skill attached. That is the entire agent-level setup
  • 3sessionUser asks; skill matches; create_app("board", "apps/<slug>"); agent writes config.json and the first data file
  • 4agentRegistry entry for this session. Nothing else changes

Failure mode to design for: the agent writes a board by hand because it did not read the skill. The registry makes this visible: an app with template: null and a slug that matches a starter name is a signal for the Build panel and for the skill's self-check.

Review queue

A starter plus a convention plus, usually, a schedule.
  • 1platformreview-queue@1 starter: lists a source folder, records decisions to review.json
  • 2agentSkill attached. The agent's own instructions say what it reviews (PRs, tickets, drafts), which is the source of the convention
  • 3agentOptional: a cron schedule that sweeps new items into the source folder each Monday. Agent proposes it; user confirms in Triggers
  • 4sessioncreate_app("review-queue", …); config.json names the source folder drafts/ and the decision set
  • 5sessionUser approves and requests changes in the app; the agent reads review.json next turn and acts

Agent-level subtlety: a scheduled sweep runs in its own session mount, not the one where the app lives. Either the app lives in the session that owns the schedule, or the review queue is placed in agent-files/apps/ as a cross-session app. The skill should ask which when a schedule is involved.

Dashboard

Read-only app; everything live is agent-level.
  • 1agentA tool connection that can produce the numbers. Without it the agent cannot fill the file and should say so instead of inventing data
  • 2agentA schedule, proposed by the agent, confirmed by the user in Triggers. The run must target the folder where the app lives
  • 3sessioncreate_app("dashboard", …); config.json names series and chart types; the first data.csv is written in the same turn
  • 4sessionUser runs it read-only. Refresh after each Monday

Same placement question as the review queue: a schedule's run writes into its own session unless the app is at agent level. A standing dashboard belongs in agent-files/apps/.

Wizard or brief

Structured input for the agent's own job.
  • 1platformform@1 starter: schema-driven steps, autosave to answers.json
  • 2agentSkill attached. The questions come from the agent's instructions: what it needs to know to do its work. That knowledge is already agent-level
  • 3sessioncreate_app("form", …); agent writes schema.json; user fills; agent reads answers next turn
  • 4agentIf the same schema is written in three sessions, that is a note and a promotion candidate: agent:campaign-brief@1 with the schema baked in as defaults

Team tools · standup

The only type that lives at agent level by design.
  • 1agentSkill rule permitting cross-session placement for this agent. Off by default in v1; on when the user asks for "something the whole team uses"
  • 2agentSlack connection for the morning post; a 09:00 schedule
  • 3platformagenta.user in the bridge hello, so the app can write people/<name>.json
  • 4agentcreate_app("agent:standup", "agent-files/apps/standup"): the instance itself is agent-level
  • 5sessionEach person opens it from any session; grant is per person per browser; writes go to their own file
  • 6agentThe scheduled run reads people/*, posts, archives to archive/<date>.json, clears

This is the type that makes the permissions section matter: everything under agent-files/apps/ is runnable by every project member who can see the agent.

Custom, then promoted

Where the registry and notes earn their keep.
  • 1agentSkill attached; the kit available
  • 2sessionNo starter matches. Agent writes index.html on the kit, app.json with template: null, data files. Registry entry says custom
  • 3sessionUser iterates; the error relay carries what broke; the app settles
  • 4agentUser: "save this as a template". promote_app writes .apps/starters/<slug>@1/ or a starter skill, strips data files, writes SKILL.md from the conversation
  • 5agentA note records why it was promoted. The instance's manifest gains template: "agent:<slug>@1"
  • 6sessionNext session's match step finds it first

Decisions

Name of the infrastructure folder
.apps/, dimmed. Consistent with .tools/. .agenta-apps/ if fully hidden is preferred.
One mount or a second named mount
One. Inside default. Revisit if starters need separate permissions.
Registry and notes as folders
Yes. One writer per file. No shared JSON at agent level.
Agent-owned starters: folder or skill
Skill, per the creation doc. The folder layout is the fallback and the transitional form.
Cross-session apps in v1
Off by default. The skill enables it only when the user asks for something team-wide.
Kit overrides
Allowed, tokens only, on explicit request. Assembler validates.
Does agent-files travel when an agent is duplicated?
Platform decision, outside apps. Either answer works; the skill drops foreign registry entries if it does.
Build panel Apps section
Phase 3 or later. Skills page plus Files pane until then.
Where a scheduled app lives
Agent level when a schedule feeds it, because the run's session is not the app's. Skill asks.
