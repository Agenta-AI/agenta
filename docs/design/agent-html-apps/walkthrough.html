One launch, one board, three hands on the same file

A single session with a launch-planning agent, frame by frame. What the user clicks, what the agent does, and every time a file is read or written along the way. Companion to the review and plan; the same bridge is stress-tested against five other app shapes in Six Apps, One Bridge.

The idea in one screen

There is no database behind an App. The session's drive is a folder of files, and the App, the agent and the user all read and write those same files. A read fetches one file's text. A write replaces one file's contents. That is the entire vocabulary.

read

Fetch one file's text. readJSON is read plus JSON.parse. The App reads on load and whenever the user hits Refresh.

write

Replace one file's whole contents. writeJSON is JSON.stringify plus write. There is no patch or append; the App sends the full new file.

list / exists / remove

Directory listing, existence check, delete. The board uses none of them; a notes app or an attachments picker would.

3

Run: the grant is the moment of consent

User picks Run, chooses what the app may touch

Choosing Run does not execute anything yet. It asks one question, in the file's folder terms. "Read" means the app can load files in launch/. "Read and write" means it can also save changes there. Nothing about the parent page, the login, or other folders is on offer, because the bridge cannot do those things.

  • ·noneNo file operation. The grant is written to memory and sessionStorage under mount 9c… / launch/ → read+write.

Running: the app reads, the user drags, the app writes

Same tab, now executing

The parent rebuilds the iframe from the same HTML, this time keeping the agent's script and injecting the bridge stub ahead of it. The app's first act is to read board.json; the columns fill. Arda drags "Write changelog" from To do to Doing. On drop, the app sends the whole updated board back as one write.

The agent sees what the user did

Turn 2 · the user never typed the change

Arda asks a question in the chat. The agent reads board.json with its own file tool, the same way it wrote it, and answers from the file's current contents. The board move became agent context without a message describing it.

6

The agent edits, the app refreshes

Turn 3 · the file changes under the running app

Arda says yes to the changelog draft and asks for a new card. The agent writes notes/changelog.md and rewrites board.json with a sixth card. There is no file watching inside the iframe, but the parent saw the drive generation change and posts a changed message naming board.json. The starter re-reads on its own when nothing is pending locally. If Arda is mid-drag, it marks the Refresh button instead and applies the change on the next quiet moment or on click.

  • 7writeagent notes/changelog.md · outside launch/; the App could not have touched this file and never needs to
  • 8writeagent launch/board.json · read, add "Blog post" to To do, write back
  • 9readapp board.json on the changed hint · the app's own load path runs again under the same grant, no prompt, no click

What if Arda had dragged a card between steps 8 and 9? The App's write would carry the pre-agent board. Without protection it would erase "Blog post". With the plan's conflict detection it cannot: the App's read in step 4 came back with an ETag, the stub sends it as If-Match on every write, and the API answers 412 because the agent's write changed the ETag. The App sees {code: "conflict"}, re-reads, reapplies the drag on top of the agent's version, and writes again. The template ships that retry. The one direction still unprotected in v1 is the agent overwriting the App, because the agent's tools write through its mounted filesystem, not the API; the skill tells it to read right before it writes.

Tomorrow: the layout comes back, execution does not

New browser session · same workspace

Arda reopens the agent the next morning. The workspace restores pane B with the board.html tab exactly where it was, but in Preview, with the same banner as step 2. The grant lived in sessionStorage, which a closed browser forgets. Restoring a layout must never start running someone's code; one click on Run, one confirmation, and the board is back with whatever the file says now.

What a write is, precisely

  • Whole file, one call. write(path, text) sends the complete new contents. The server replaces the object. No append, no patch, no partial update.
  • Text only in v1. UTF-8 strings. writeJSON is a convenience that stringifies for you. Binary uploads stay with the Files pane.
  • Relative to the HTML file. "board.json" from launch/board.html means launch/board.json. "../notes/x.md" is rejected before any request with {code: "scope"}.
  • Resolved means stored. The promise resolves after the API returns, so a "Saved" toast is true. A rejection carries a code the app can branch on: read_only, scope, not_found, conflict, too_large, unavailable.
  • Conditional by default. Every read hands the stub an ETag for that path. Every write sends it as If-Match. If anyone changed the file since you read it, the write fails with conflict instead of erasing their change. Pass {force: true} to overwrite anyway.
  • Visible to everyone at once. The Files pane re-lists on the next drive generation; the agent's next read sees the bytes. There is no cache between writers, only the running App's in-memory copy, which Refresh replaces.
  • Same permission as the user. If Arda cannot edit this drive, "Read and write" is not offered, and a write would fail at the server anyway.

Three interactions, one event

Moving a card, adding a card, and adding a column all produce the same single event across the boundary: one write of board.json. The bridge has no vocabulary for cards or columns. The only thing that differs between the three is the text inside the body.

Each interaction has two halves. The first half stays inside the iframe: a browser event, the app's own handler, a change to the in-memory board object, a re-render. The second half is what crosses to Agenta, and that half is identical every time.

What follows from "one event"

  • No per-action audit at the platform level. Agenta can log "board.json written by app at 22:41, 490 B". It cannot log "card added". If that matters, the app writes its own board.log.json, or the format carries a history array.
  • No per-action permission. The grant is read or read+write for the folder. "May move cards but not add columns" is not expressible, and should not be in v1; that is the app's job, driven by its own data.
  • Undo is the app's, not the bridge's. The app keeps previous states in memory if it wants undo. The bridge only ever sees the latest whole file.
  • The agent reads meaning from structure. When the agent later reads board.json, "Record demo is in Doing" is a fact about the file, not an event it received. This is why the data file should be plain and stable: the agent's understanding depends on it.
  • Payload grows with the board. A hundred cards is still a few kilobytes and one PUT. A board that outgrows a single file is a sign to split the data, not to invent a patch protocol.

Could there be semantic events? A future agenta.events.emit("card.moved", {…}) is possible and is not in PR #6529. It would need a consumer (the agent, a log, a trigger) and a schema per app type, which is exactly the "broad application platform" the proposal says to avoid until we know which apps people build. Files first; events only when a real consumer appears.

Who defines what, and who calls the API

Two questions come up every time someone reads the code above. Are moveCard and friends part of Agenta? And if the app has no API access, who makes the HTTP call? The answers are "no" and "the Agenta frontend".

The frontend is the caller

"Apps have no API access" means the iframe holds no cookie, no token, and no HTTP client, so it cannot reach the server on its own. It can do one thing: send a message to the page that contains it. The Agenta frontend receives that message, decides whether it is allowed, and makes the real API call using the user's own session. Read top to bottom, one addCard goes like this:

  1. The agent's addCard runs inside the iframe and calls agenta.fs.writeJSON("board.json", board).
  2. That function is the stub. It does no HTTP. It posts {id, method: "write", path, body} over the MessageChannel port and parks a promise under the id.
  3. The Agenta frontend, the HtmlBody component that owns the iframe, receives the message and checks: the port is its own, the grant allows writes, the path resolves inside launch/, the body is under the size cap.
  4. If all pass, the frontend calls writeMountFile on the Fern client with the user's session cookie. To the server this is indistinguishable from the user uploading the file from the Files pane.
  5. The response returns to the frontend, which posts {id, ok, result} back over the port. The stub resolves the parked promise, and the agent's await completes.

So the frontend is a proxy that forwards a fixed list of eight file operations and nothing else. That is why the grant checks live in the frontend, why the folder scope is a frontend guardrail, and why the server cannot tell an app write from a user write.

Where this comes from

This flow is PR #6529's proposal, not an invention of this walkthrough. Mahmoud's design says each bridge method "sends a request to the parent window through postMessage. The parent validates the message source, resolves the path, checks the grant, calls the workspace file API, and sends back a result or a structured error", and that "the parent performs approved operations on the application's behalf." The board example, readJSON then writeJSON, is his too.

Added by the review, on top of that contract: a MessageChannel port instead of postMessage("*") with a source check; the name window.agenta instead of window.arg; a CSP meta and tighter sandbox flags; shipping read and write together behind one grant; the grant kept in memory and sessionStorage; the drive-generation bump after a write; the frozen error-code list; and the module placement in @agenta/entities and @agenta/entity-ui. The "one event" framing and the moveCard handlers are exposition of his contract, not changes to it.

The app's code, the parts that matter

This is roughly what the agent wrote in step 1, minus styling and the drag handlers. Everything the app knows about Agenta is the agenta global. It could be developed against a stub that reads and writes localStorage, which is how templates should be tested.

<!-- launch/board.html -->
<div id="board">Loading board…</div>
<script>
  const FILE = "board.json"
  let board

  async function load() {
    await agenta.ready                      // handshake done, grant known
    board = await agenta.fs.readJSON(FILE)  // 1 read
    render()
  }

  function render() {
    // draw board.columns[*].cards as three lists with draggable items;
    // on drop, call moveCard(text, fromId, toId)
  }

  // every interaction ends here: one whole-file write
  async function save(label) {
    if (!agenta.canWrite) return toast("Read-only: change not saved")
    try {
      await agenta.fs.writeJSON(FILE, board)   // the one event; If-Match sent by the stub
      toast(label + " · saved board.json")
    } catch (e) {
      if (e.code === "conflict") {             // someone wrote since we read
        const theirs = await agenta.fs.readJSON(FILE)
        board = mergeCards(theirs, board)      // reapply our move on their version
        render()
        return save(label)                     // one retry, now with the new ETag
      }
      toast(e.code === "read_only" ? "Read-only" : "Couldn't save")
    }
  }

  async function moveCard(text, fromId, toId) {      // drop
    const from = board.columns.find(c => c.id === fromId)
    const to   = board.columns.find(c => c.id === toId)
    from.cards = from.cards.filter(t => t !== text)
    to.cards.push(text)
    render(); await save("Moved")
  }

  async function addCard(colId, text) {              // submit
    board.columns.find(c => c.id === colId).cards.push(text)
    render(); await save("Added")
  }

  async function addColumn(title) {                  // click
    const id = title.toLowerCase().replace(/\W+/g, "-")
    board.columns.push({ id, title, cards: [] })
    render(); await save("New column")
  }

  load()
</script>

What the agent needs to know to write this. Four facts, which belong in a skill or the system prompt: apps are HTML files in the drive; data goes in a sibling JSON file; the API is agenta.fs with readJSON and writeJSON relative to the HTML file; wait for agenta.ready and respect agenta.canWrite. That is the entire onboarding surface for the agent.
