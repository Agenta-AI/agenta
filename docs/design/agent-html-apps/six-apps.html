Agenta · agent HTML apps · field test on paper

Six apps, one bridge

The launch board proved the loop. This page pushes the same file bridge through six different app shapes to see where it holds, where it strains, and where it cannot go. Each case is end to end: files, flow, a mockup, the operations, and a verdict. Companion to the plan and the walkthrough.

How to read this

Every case is built only from what PR #6529 proposes: an HTML file in a drive, opened in Run mode, with agenta.fs offering read, readJSON, write, writeJSON, list, exists and remove, scoped to the file's folder, and nothing else. The cases were chosen to each lean on a different capability the board never touched:

#AppWhat it probes
1Changelog review queueMany files, list, remove, moving a file between folders, rendering markdown
2Grading sheet for eval resultsA large input file, frequent writes, two writers that never collide
3Team standup boardThe agent drive instead of a session drive, cron runs, several people, identity
4Metrics dashboardRead-only grant, charts with no CDN, data the app cannot fetch itself
5Campaign brief wizardStructured input for the agent, and how the app hands control back
6Multi-page docs siteSeveral HTML pages, a shared script file, navigation while running

Convention note: these cases were written before the folder convention in the creation doc. Under it, each app is apps/<slug>/index.html beside an app.json manifest, so changelog/review.html reads as apps/changelog-review/index.html. Nothing else about the cases changes.

Verdicts use three words. Fits: works as proposed. Strains: works with a pattern the template must teach, or a small addition. Gap: the design cannot do it, and the page says whether that is acceptable.

1

Changelog review queue

Probes · many files · list · remove · move between folders · markdown

A release manager asks the changelog agent to draft entries for every merged PR of the week. The agent writes one markdown file per PR into a drafts folder and an app to review them. The user approves, sends back, or rejects each draft; approved ones move to a folder the docs pipeline reads.

Files
changelog/
  review.html          ← the app
  review.json          ← app writes: decisions
  drafts/
    6529-run-mode.md    ← agent writes
    6775-workspace.md
    6802-turn-pulse.md
  approved/
    6802-turn-pulse.md  ← app "moves" here
Bridge methods used
list("drafts")read(path)writeJSON("review.json")write("approved/…")remove("drafts/…")exists
Grant
Read and write on changelog/

End to end

  • 1write ×4agent review.html and three drafts under drafts/. Folders need no create call; writing a nested path is enough on an object store
  • 2listapp list("drafts") → three entries with name, size, modified
  • 3read ×3app one read per draft, fired in parallel; the stub matches replies by id
  • 4readJSONapp review.json; not_found on first run, which the app treats as empty
  • 5writeJSONuser clicks Request changes on 6775 with a note → review.json gains {"6775": {"status": "changes", "note": "…"}}
  • 6writeuser clicks Approve on 6802 → app writes approved/6802-turn-pulse.md with the draft's text
  • 7removeapp drafts/6802-turn-pulse.md. Steps 6 and 7 are the "move". They are two calls, not one
  • 8readagent next turn: reads review.json, rewrites the draft with changes requested, replies "Updated 6775, ready for another look"
Fits
  • Many small files is the bridge's natural shape
  • Parallel reads by id keep it fast enough for dozens of drafts
  • Decisions in one JSON file give the agent a single thing to read
Strains
  • No move: copy then remove is two calls, and a failure between them leaves the draft in both folders
  • Markdown rendering must be inlined; the template ships a small renderer or the agent writes drafts as HTML fragments
Gap
  • None that blocks it

Plan impact: fs.move is a candidate for v2. Not required; the template can order the two calls write-then-remove so the worst case is a duplicate, never a loss.

Grading sheet for eval results

Probes · large input · frequent writes · two writers · JSONL

An engineer asks the agent to run a prompt over 300 test cases and let them grade the outputs by hand. The agent writes the outputs as JSON Lines and an app that shows one row at a time with a 1 to 5 scale and a comment box. The grades go to a separate file the agent turns into a report.

Files
eval/
  grade.html        ← the app
  results.jsonl     ← agent writes, 300 rows, ~180 KB
  grades.json       ← app writes, ~20 KB when full
  report.md         ← agent writes at the end
Bridge methods used
read("results.jsonl")readJSON("grades.json")writeJSON("grades.json")
Pattern
One writer per file. The agent owns results.jsonl; the app owns grades.json. They never overwrite each other.

End to end

  • 1write ×2agent results.jsonl after the batch, then grade.html
  • 2readapp read("results.jsonl") as text, splits on newlines, parses each row. readJSON would fail on JSONL, so the template uses read
  • 3readJSONapp grades.json to resume where the user left off; not_found means start at row 1
  • 4writeJSON ×~60user grades 300 rows over an hour. The app debounces saves to one per 500 ms of quiet, so a burst of clicks is one write of the whole grades file
  • 5readagent "Summarize the grades" → reads grades.json, computes the distribution, writes report.md, and can also push the graded rows into an Agenta testset with its own tools
Fits
  • Separate files per writer removes the concurrency question entirely
  • Whole-file writes of 20 KB every half second are trivial for the API
  • Resume after reload is free: state is in the file
Strains
  • A size cap must exist and must be known. 180 KB is fine; a 20 MB results file is not. Proposal: 4 MB per read, 1 MB per write, both errors surfaced as too_large
  • No partial read: the app loads all 300 rows to show one. Acceptable to a few MB
Gap
  • Very large datasets. Above the cap, the agent must shard into results-1.jsonl, results-2.jsonl and the app lists and pages them

Plan impact: the size caps are a decision the plan should record in the contract, not leave to the implementation.

Team standup board

Probes · agent drive not session drive · cron trigger · several people · identity

A team uses one agent for daily standups. Each morning a scheduled run posts yesterday's board to Slack and clears it. During the day each person opens the board and types their three lines. This app must outlive any single session, so it lives in the agent's own drive, which every session of that agent and every trigger run can see.

Files · in the agent drive
standup/
  board.html
  today.json        ← everyone writes  ⚠
  people/
    arda.json       ← one file per person (better)
    mahmoud.json
  archive/
    2026-09-16.json ← cron run writes
Bridge methods used
list("people")readJSONwriteJSON("people/<me>.json")agenta.user
Grant
Read and write on standup/, keyed per person per browser session

End to end

  • 1writeagent standup/board.html into the agent drive, on request from whoever set the standup up
  • 2list + readapp Arda opens the board from a file card; list("people") then one readJSON per file to show everyone's lines
  • 3writeJSONuser Arda types three lines → people/arda.json. The app needs to know it is Arda to pick that path; today it cannot
  • 4writeJSONuser Mahmoud, in his own session, writes people/mahmoud.json. Arda's open board does not see it until Refresh
  • 5read ×Ncron 09:00 run reads every people/*.json with its file tools, formats the post, sends via the Slack tool
  • 6write + removecron writes archive/2026-09-16.json, clears the people files. No bridge involved; the agent's tools have the full drive
Fits
  • Agent drive gives cross-session and cross-run persistence with no new machinery
  • Grants are keyed by mount and path, so the same file works from any session
  • Cron runs never touch the bridge; they are ordinary agent turns with file tools
Strains
  • The app has no idea who the user is. A sandboxed iframe has an opaque origin, so it cannot even remember a name in localStorage. Proposal: agenta.user = {id, name} in the hello. It is the user's own name shown in their own browser; no new reach
  • No push between people. The parent's changed hint covers it once the other person's write lands; the app re-reads when nothing is pending locally
Gap
  • Real-time collaboration, and only because this app sits in the project-wide agent drive. Session-drive apps are one user by construction. Two people on one file is last-writer-wins; per-person files are the answer

Plan impact: add agenta.user to the v1 hello payload. It is one field and it unlocks every multi-person app.

Metrics dashboard

Probes · read-only grant · charts without a CDN · data the app cannot fetch

A founder asks the agent for a weekly view of token spend and latency per agent. The agent has tools that can query Agenta's own analytics; the App has none. So the agent pulls the numbers, writes a CSV, and writes a dashboard that only reads. A cron trigger regenerates the CSV every Monday.

Files
metrics/
  dashboard.html    ← the app, read-only
  weekly.csv        ← agent writes (cron, Mondays)
  notes.md          ← agent's commentary
Bridge methods used
read("weekly.csv")read("notes.md")fetch(analytics API)<script src="cdn/chart.js">
Grant
Read only on metrics/. The write option is never needed, so the user is not asked for it

End to end

  • 1write ×2agent queries analytics with its tools, writes weekly.csv and dashboard.html
  • 2read ×2app on load: weekly.csv parsed by a 10-line CSV splitter, notes.md shown as text
  • 3writecron Monday 09:00 run rewrites weekly.csv
  • 4readapp Monday afternoon the tab is open; the parent posts changed for weekly.csv and the app re-reads on its own. A closed tab simply reads the new file on open. "Ask agent to refresh data" in the Refresh menu is for the week the schedule did not run
Fits
  • Read-only grant means the prompt is one click and the app can never damage anything
  • Cron plus CSV gives a schedule without any live infrastructure
  • Hand-drawn SVG charts are well within what an agent writes reliably
Strains
  • No CDN. A charting library must be inlined into the HTML (200 KB for Chart.js) or avoided. The template should default to SVG and say so
  • "Data as of" must be visible; fs.stat gives the real mtime so the app does not guess
Gap
  • Live data. The App cannot call any API. Today's spend, new tickets, CI status, an LLM call: all must arrive as a file the agent wrote, on request or on a cron

Plan impact: none to the contract. Template guidance: charts as SVG, CSV over JSON for tabular data, always render the file's modified time.

Campaign brief wizard

Probes · structured input for the agent · handing control back to the conversation

A marketer wants the agent to write campaign copy but keeps forgetting to give it the audience, the tone, the channels and the dates. The agent writes a six-step wizard that collects exactly what it needs into a JSON file, and the marketer fills it in beside the chat. Then the marketer wants one button: "send this to the agent".

Files
brief/
  wizard.html       ← the app
  schema.json       ← agent writes: the questions
  brief.json        ← app writes: the answers, autosaved
  copy/
    email-1.md      ← agent writes after reading brief.json
Bridge methods used
readJSON("schema.json")readJSON("brief.json")writeJSON("brief.json")agenta.chat.draft(text)
Grant
Read and write on brief/

End to end

  • 1write ×2agent schema.json with six questions and their field types, and wizard.html which renders any schema
  • 2readJSON ×2app the schema, then brief.json to resume a half-finished brief
  • 3writeJSON ×6user one write per completed step; the whole brief each time
  • 4—user clicks Send to agent. v1: the app shows "Tell the agent the brief is ready". Proposed: the composer fills with that sentence and the user presses Send
  • 5readJSONagent reads brief.json, writes copy/email-1.md and copy/linkedin-1.md, replies with file cards
Fits
  • Schema-driven forms are exactly what an agent writes well and a file stores well
  • Autosave per step means a closed tab loses nothing
  • The agent's next turn has structured input instead of a paragraph
Strains
  • Handing back to the agent. The App cannot send a message, and should not. A composer prefill is a parent-side feature: the iframe posts text, the parent writes a draft, the user sends
Gap
  • Autonomous action. An App that triggers a run by itself would be a new capability class with real risk. Not proposed

Plan impact: agenta.chat.draft(text) as a v1.1 method. Small, host-side, and it turns "fill a form" into "fill a form and go".

Multi-page docs site with a shared script

Probes · several HTML pages · a script in its own file · navigation while running · state across pages

An agent generates internal docs for a project: an index page, one page per module, a search box backed by a JSON index, and a shared app.js for the search and navigation. This is what agents write when asked for "a small site". It is also the case that exposes two things the current assembler does not do.

Files
site/
  index.html
  guide.html
  api.html
  app.js            ← shared script  ⚠ assembler strips scripts
  site.css          ← inlined today ✓
  search-index.json ← app reads
Bridge methods used
readJSON("search-index.json")<script src="app.js"> in Runnavigate in-tab under the same grantagenta.location
Grant
Read only on site/

End to end

  • 1write ×6agent three pages, the shared script, the stylesheet and the search index
  • 2read ×2app the assembler fetches site.css (already does) and app.js (new) from the mount and inlines both before injecting the bridge
  • 3readJSONapp app.js loads search-index.json on first keystroke in the search box
  • 4read ×2user clicks a result linking to guide.html?q=api. Proposed: the parent re-assembles guide.html in the same tab under the same grant and passes location in the hello, so app.js can highlight the query
  • 5readuser clicks a link to ../README.md. Outside site/, so it opens in the drive as today, in Preview, in another tab
Fits
  • Static multi-file sites already assemble, minus scripts
  • Read-only grant is enough for a site; nothing writes
Strains
  • Must fix for v1: Run has to inline same-folder <script src> files, exactly as it inlines CSS. Without this, every app with a separate script file is broken
  • Should fix for v1: in-folder links navigate the running tab and keep the grant. Otherwise each click opens a new inert tab
  • agenta.location in the hello is one field and makes query strings work
Gap
  • Cross-page state. An opaque origin has no storage, and there is no URL. Anything that must survive navigation goes in a file or in the query string

Plan impact: two items move into phase 1 work package 1.4. The assembler change is small; the navigation change touches the nav interceptor the preview already has.

Net read. The bridge handles every "edit structured state beside the conversation" app the six cases threw at it, which is the product loop #6529 set out to enable. It exposed two real bugs in the Run assembly path, both cheap, and three one-field additions that widen the range without widening the security surface. The things it cannot do are the things it should not do.
