Canvas apps: a todo list as a whiteboard

Everything so far has been DOM: columns, forms, tables. A canvas app draws its own pixels: a whiteboard with sticky notes and pen strokes, a chart of a hundred thousand points, a diagram with connectors. The sandbox already allows all of it. What changes is which files an app needs, how state has to be shaped so two writers can merge, and how libraries reach the page. Companion to the plan, creation and layout.

What works in the sandbox today

The Run iframe is sandbox="allow-scripts allow-forms" with an opaque origin and a CSP that forbids external scripts. Against that, canvas features sort into three groups.

2D canvasWorks
Drawing, text, images from data URLs, hit testing, HiDPI via devicePixelRatio. Nothing about a sandbox touches it.
WebGL and WebGL2Works
Available in sandboxed iframes. GPU access follows the browser's policy; a headless or low-power context may fall back. Fine for viz; not needed for a whiteboard.
Pointer, touch, wheel, keyboardWorks
Events inside the iframe are the app's. Pinch-zoom on a phone works if the app handles touch itself; the host does not intercept.
OffscreenCanvas and WorkersWorks with one CSP line
Workers from a blob URL run in an opaque origin, but the v1 CSP is default-src 'none'. Add worker-src blob: when a starter needs it; leave it off otherwise.
WebAssemblyOff by default
Needs 'wasm-unsafe-eval' in script-src. Some viz and layout libraries ship WASM. Enable per library on the shelf, never globally.
Loading an image by pathDoes not work
new Image().src = "photo.png" has no base URL in a srcdoc document. The assembler inlines <img> tags today, not JS loads. Needs an asset preload or a binary read.
Exporting a PNGDoes not work
canvas.toBlob() produces bytes; the bridge writes text only. Export as SVG works today for vector content. Binary write is a v2 method.
Fonts on canvasWorks, system fonts
Canvas text uses whatever font resolves to. The kit's stack is system fonts, so canvas text matches DOM text with no loading step.
Persisting between rendersWorks, in files
Opaque origin means no localStorage. The scene lives in memory and in the data files, same as any app. That is the constraint that shapes the format below.

The whiteboard, end to end

Same launch as the walkthrough, different surface. Arda asks for the launch tasks "as a whiteboard I can move around and scribble on". The agent instantiates the whiteboard starter and writes the tasks as sticky notes placed inside three regions. Arda drags notes between regions, draws an arrow, ticks one done. The agent reads region containment the same way it read columns before.

Why two data files
Strokes churn on every pen stroke and grow large; notes change rarely and the agent cares about them. Splitting keeps the agent's file small and the writes cheap. One writer per file still holds: the app owns both, the agent reads board.json and may add to it.

End to end

  • 1writeagent create_app("whiteboard", …), then config.json with three regions and board.json with five notes placed inside "Today" and "This week", using the starter's placement rule: next free slot in the region's grid
  • 2readJSON ×2app on load: both files; strokes.json is not_found and treated as empty
  • 3writeJSONuser drags "Write changelog" into Done and ticks it. One write of board.json on drop; the note's updated_at changes, and its geometry is now inside the Done region
  • 4writeJSON ×nuser draws an arrow. Points accumulate in memory during the stroke; one write of strokes.json on pointer-up, debounced 300 ms across consecutive strokes
  • 5readagent "What's left for today?" → reads board.json, computes containment of each note's centre in each region, answers "Record demo and Draft announcement". It never opens strokes.json
  • 6writeagent "add a note for the webinar" → appends an object to board.json at the next free slot in Today. Meanwhile Arda is still dragging; the app's next write carries an old ETag, gets conflict, merges by object id, and retries. Nothing is lost
  • 7writeuser Export → the app serializes the scene to SVG and writes export.svg. A file card appears in the chat on the next turn if the user asks for it

A data format that merges

The board's columns were arrays, and a conflict meant "re-read, reapply my move". A whiteboard has two writers who both change geometry, and arrays cannot be merged by position. The whiteboard starter therefore uses a map of objects keyed by id, each stamped with updated_at, and deletions as tombstones. Merging two versions is then a union by id, latest wins per object. The agent can add a note without knowing what the user is dragging.

"Latest wins" is only a rule if it is a total order, so the format fixes the comparison rather than leaving it to whoever implements the starter. updated_at is RFC 3339 in UTC with millisecond precision (2026-09-18T09:31:44.218Z), and each object carries by, either "app" or "agent". Compare updated_at first; on an exact tie the app value wins, because a tie means the person moved that object and is looking at it while the agent wrote blind. Two writes from the same side cannot tie on the same object: they are serialised by If-Match on the file, and the loser re-reads before retrying.
Worth being clear about what this is not. It settles which value a reader keeps; it is not a claim about ordering two edits in real time, because the two clocks are not the same clock. If-Match is still what stops a whole-file clobber. The tiebreak only decides the case that ETags cannot see, which is two different values for one object with the same stamp.

Points are [x, y, pressure] in board coordinates, not screen pixels, so zoom and pan never rewrite them. A stroke of two hundred points is about 4 KB; a busy board's strokes file stays under the write cap for a long time.

The same format is what the skill tells the agent to read. "Notes in region R" is a containment test on centres; "done" is a flag; "add a note" is one new object at a free slot. None of it needs the agent to understand drawing.

Libraries without a CDN

The CSP blocks external scripts, and inlining d3 into every app's HTML costs 280 KB per app and invites the agent to paste a mangled copy. The answer is a curated shelf: Agenta ships a small set of pinned, hash-checked library builds, and the assembler inlines the ones an app declares. The app's HTML stays small, the bytes are identical everywhere, and the CSP is untouched because nothing is fetched at run time.

Not on the shelf, deliberately: React, tldraw, Excalidraw, Chart.js, Three.js. Each is either a framework, a product, or large enough that a starter should own the decision. The shelf is small on purpose; adding to it is a review, not a config change.

Why not let the agent inline what it wants? It can, and custom apps may. But a pasted library is a 280 KB opportunity for a transcription error, and two apps with two slightly different d3s are the drift problem again. The shelf is the starter idea applied to code the agent did not write.

The canvas helper

Most of what makes a canvas app pleasant is the same forty lines every time: size the backing store to the device pixel ratio, resize with the pane, pan with space-drag and zoom with the wheel, convert between screen and board coordinates, hit-test objects, throttle the render loop, and pause when hidden. The helper is that code, shipped on the shelf, so a starter or a custom app calls it instead of rewriting it.

agenta-canvas.js · surface
const view = agentaCanvas.mount(el, {
  grid: "dots",                 // or null
  bounds: "infinite",           // or {w, h}
  onPointer: (ev, board) => …,  // ev.kind: down/move/up; board.x, board.y
  render: (ctx, camera) => …    // called at most once per frame
})
view.toBoard(sx, sy) · view.toScreen(bx, by)
view.hit(list, bx, by)          // first object whose rect contains the point
view.camera = {x, y, zoom}      // pan/zoom state; the app may persist it
view.invalidate()               // request a render
view.exportSVG(draw)            // same draw callback, SVG context
view.paused                     // true when the host says the tab is hidden
What it does not do
  • No scene graph, no shapes, no undo. The starter owns its objects; the helper owns the viewport
  • No persistence. Files are the app's business through the bridge
  • No text editing. Notes edit in a DOM overlay positioned by toScreen, which is how every whiteboard does it and how the kit's inputs stay accessible
  • No collaboration. The merge-by-id format covers the two writers we have

Data visualization

The dashboard starter draws SVG by hand, which is right up to a few thousand marks. Beyond that, SVG DOM cost dominates and canvas wins. The rule the skill gives is a threshold, not a preference.

Two things stay true from the field test's dashboard: the app cannot fetch anything, so the data file is the boundary; and "data as of" must be visible. Canvas adds one more: a large dataset lives in its own file with its own size cap, and a starter that expects more than the read cap tells the agent to shard, not the user to wait.

Hidden tabs and render loops

A DOM app that is in a background tab costs nothing. A canvas app with a requestAnimationFrame loop keeps drawing. The browser throttles rAF only when the whole page is hidden, and in the workspace a hidden tab is still on a visible page. The RFC for the workspace says iframes "need explicit suspension"; this is the concrete form.

agenta.visible and a visibilitychange event on the stub are one field and one message. They belong in the v1 contract because the workspace's hidden-tab policy needs them the moment a second tab exists, canvas or not: a DOM app polling a timer should stop too.

What canvas cannot do

  • Be read by a screen reader. Pixels are not text. The whiteboard starter keeps a DOM list of notes under the canvas, visually hidden, generated from the same objects. The same list is what a phone shows below md where a pan-and-zoom surface is miserable. Cost: none, the data is already there.

    That list is the keyboard surface, not just a readout, so every state a pointer can reach has a control in it. Each note is a list item holding a real <input type="checkbox"> labelled with the note text, so Space toggles done; a Connect to… button opens a listbox of the other notes and choosing one writes the connector; a connector row carries its own Remove button. All four go through the same object mutation, the same updated_at stamp and the same If-Match write as the pointer path, so there is one write path and not two. An aria-live="polite" region announces the result (marked done, connected Draft announcement to Record demo, and any save failure), because the visual feedback a canvas gives is exactly what a keyboard user does not get. The move-items menu the starter already specifies stays as it is; this covers the two actions it does not reach.

  • Use the kit's classes. Buttons and inputs still do; the drawing does not. The helper reads the kit's tokens for grid, selection and text colours so the surface matches the theme, and re-reads them on the theme message.
  • Load an image by path. Until binary reads exist, a starter that needs images declares them in the manifest and the assembler preloads them as data URLs into agenta.assets. That covers icons and a logo; it does not cover a user dropping a photo onto the board, which needs binary write as well.
  • Export a PNG. SVG export works today and is the better artefact for a whiteboard anyway: the agent can read it, and it scales. PNG waits for binary write.
  • Keep state between reloads. No storage in an opaque origin. The camera position is worth persisting, so the starter writes it into config.json under view, debounced, and restores it on load.

What did not change. The bridge's eight methods, the sandbox flags, the grant model, the folder scope, the conflict detection. A canvas app is a DOM app that happens to draw. Everything above is about making it easy to write one that behaves.

Decisions

Ship a library shelf at all?
Yes, small. Seven entries, one heavy. Additions are reviewed, not configured.
Which canvas starter first?
whiteboard@1. It is the todo list on a new surface and exercises every new piece.
Visibility signal in v1?
Yes. One field, one message; the workspace needs it for DOM apps too.
Asset preload or binary read first?
Preload. It is the assembler's existing inlining, declared in the manifest. Binary read stays v2.
Helper as a shelf lib or part of the kit?
Shelf. Declared with "libs": ["canvas"]; DOM apps never pay for it.
WebGL?
Allowed, not supported. Nothing on the shelf uses it; a custom app may.
Strokes in a separate file?
Yes. Churn and size differ from notes by an order of magnitude, and the agent never reads strokes.
