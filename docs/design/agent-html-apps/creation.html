How apps get made, and made the same way twice

The bridge decides what a running app can do. This page is about the step before that: how an agent turns "make me a board" into a folder of files, how two sessions asking for the same thing end up with the same app, and how a user tells an app from a file. Companion to the plan, the walkthrough and the field test.

One way in

An app is created by an agent, during a turn, using its file tools, the same way it writes any other file into the session's drive. There is no app builder, no upload path, and no separate "create app" screen. The user asks for something in the conversation; the agent decides it is an app; a folder appears.

PR #6529 says exactly this much: "an agent writes a small application as HTML, CSS, and JavaScript", with "starter templates" deferred to a later slice. It does not say how the agent knows the bridge exists, what a well-formed app looks like, how a user recognizes one, or how the agent fixes one it cannot see running. Those are the four things below, and one of them, consistency, is the one that decides whether the feature feels like a product or like a lottery.

The drift problem

Take one agent and two sessions. In both, the user asks for a task board. Without anything constraining it, the agent writes two boards from scratch, and they will not match. Different columns, different colours, different keyboard behaviour, one with drag and one with buttons, one that saves on every change and one that has a Save button. The user's mental model is "my agent has a board". The reality is two unrelated programs that happen to share a name.

Two mechanisms, in order of strength:

  1. Starters are copied, not generated. For the common shapes, the agent never writes the HTML. A platform operation copies a versioned starter, byte for byte, into the session folder. The agent's only creative act is writing the data and a small config file. Two sessions get identical apps because the bytes came from the same place.
  2. Custom apps are built on the design kit. When no starter fits, the agent writes HTML, but the page's look comes from a stylesheet Agenta injects, with the host's theme tokens. Two custom apps will differ in structure and still read as siblings, in the same way two Agenta pages do.

Starter or custom

Tier 1 · preferred

Starter app

  • Agent calls create_app(starter, dir), a platform operation. The API copies the starter's files into the folder
  • Agent then writes only the data files and config.json (title, columns, fields)
  • app.json records "template": "board@1", so the app is recognizable and upgradable
  • Identical across sessions, agents and projects
Tier 2 · when nothing fits

Custom app

  • Agent writes index.html itself, following the skill's rules
  • Uses the design kit classes and tokens; no external scripts; data in sibling files
  • app.json has no template; the kit still applies
  • Coherent with starters in colour, type and controls; structure is the agent's

The app folder

An app is a folder, and what makes a folder an app is a manifest file in it. Not a file extension, not a heuristic on the HTML source. The explorer, the file cards, the Run tab and the agent all read the same small file.

Recognition is by manifest only. The explorer never guesses from an HTML file's contents, so an ordinary HTML document the agent wrote for reading is never mislabelled as an app.

How the agent learns

Nothing in the bridge is discoverable by an agent. It has to be told that apps exist, when to make one, how the folder is shaped, and which starters it can copy. The mechanism for teaching an agent a procedure already exists in Agenta: a skill in the skill registry. The proposal is one platform skill, agenta-apps, attached by default to any agent that has a drive.

agenta-apps · SKILL.md, the shape of it

Six covers the field test and the walkthrough. Each starter is a real HTML file in the API's starter bundle, versioned as name@N, and copied verbatim by create_app. Canvas starters, whiteboard, chart and diagram, are specified in Canvas Apps and join the catalogue in phase 3.

Why a platform operation, not a reference file

The skill could carry the starters as reference files and let the agent read and re-type them. That costs tokens per creation and, worse, invites drift: a model retyping 300 lines will "improve" a few. create_app is a platform op like the existing search_skills: the API copies the starter's files into the mount and returns the paths. No tokens, no drift, and the manifest's template field is stamped by the platform, not by the model.

Delivery. agenta-apps is a first-party skill in the registry, auto-attached to agents that have a drive, visible in the agent's Skills section like any other, and updated through the registry's refresh flow. Users who do not want their agent making apps can detach it. That is the entire configuration surface.

The design kit

Starters give identical apps. The kit is what makes custom apps, and starters, look like they belong to the same product and to the host they run in. It has two parts, both injected by the assembler when app.json says "kit": true: the host's theme tokens, and a small base stylesheet.

agenta-app.css · scope
  • Reset and type: 12 px base, the host's font stack, tabular numerals for tables
  • Layout: .ag-app, .ag-toolbar, .ag-columns, .ag-column, .ag-list, .ag-grid
  • Controls: .ag-btn, .ag-btn-primary, .ag-input, .ag-select, .ag-check
  • Surfaces: .ag-card, .ag-badge, .ag-empty, .ag-toast
  • States: [data-dragging], [aria-busy], focus rings that match the host
  • Under 6 KB. Not a component library; a house style
What it buys
  • A custom review queue and a starter board share buttons, cards, spacing and colour, so they read as one product
  • Dark mode for free: the app never hard-codes a colour
  • The skill can say "use .ag-btn-primary for the main action" instead of describing a button
  • Starters are written on the same kit, so a custom app made next to one does not look foreign

The kit ships with the assembler, in @agenta/entity-ui, versioned with the bridge. An app that sets "kit": false gets tokens only, for the rare case where the agent has a reason to own the whole look.

The creation loop

The agent cannot run the app. It has no browser. Everything it learns about whether the app works comes from the user, and today that means the user describing a broken page in words. The loop below closes that gap by letting the Run tab relay what went wrong.

What the relay carries

  • Bridge rejections the app did not catch: not_found, scope, read_only, with the method and path. These are the common creation mistakes.
  • Script errors: the stub listens for window.error and unhandledrejection and posts message, file and line over the port. A typo in index.html shows up as a line number instead of a blank page.
  • Nothing else. No console log stream, no DOM, no screenshots. Errors only, and only to the user's own screen. Sending them to the agent is the user's click, through the composer draft.

Before the composer prefill exists, the strip has a copy button. The relay is useful on day one; the one-click send is what makes it feel finished.

Grants while building

During creation the agent rewrites index.html on most turns. A grant tied to the file's contents would ask the user to approve every edit, which is friction that trains people to click through. The grant is therefore tied to what it actually protects: the folder and the access level. It survives edits to any file in the folder. Run asks again only when the entry moves to another folder, when the app requests more access than it was given, or when the browser session ends. The plan's grant lifecycle is updated to say this.

The grant prompt is built with a third section from the start, hidden until tier 2: per-connection, read-only tool access. Nothing in v1 or v1.1 shows it; reserving the layout means the prompt does not get redesigned later.

One consequence for the manifest: access is a request, not a grant. The prompt preselects it, and the user can still choose read-only. An app that then tries to write gets read_only, shows it, and the relay carries it if the user wants the agent to know.

What the skill enforces

The rules a custom app must follow, and that every starter already follows. They exist so that an app made in any session by any agent behaves like every other one.

  • One folder per app under apps/<slug>/, with app.json and index.html. Data and config as sibling files.
  • Check for an existing app.json before creating. Update, never duplicate.
  • Prefer a starter. Custom only when the catalogue has nothing close.
  • "kit": true. Use kit classes and tokens; no hard-coded colours or fonts.
  • No <script src> or <link> to the internet. Libraries are inlined or avoided; charts are SVG.
  • Wait for agenta.ready. Respect agenta.canWrite; disable or label write actions when false.
  • Small JSON data files, each with one primary writer: the app, while it is open. The agent may write the same file, and for several starters it is meant to. What keeps that safe is reconciliation, not exclusivity. Whole-file writes, debounced. The app handles conflict by re-reading and reapplying, once, on an If-Match the stub sends for it. The agent reads a data file immediately before writing it, because its own writes are unconditional and it has no ETag to carry.
  • Show "data as of" for anything the agent produces on a schedule. Handle not_found as empty state, not as a crash.
  • After creating, reply with the file card, say what access the app needs, and tell the user to choose Run.

Agent-level layout

Everything so far lives in a session. Some things have to live with the agent, so that every session, and every scheduled run, sees the same setup. There are two kinds: files in the agent's durable folder, and configuration on the agent entity that is not a file at all. Both are listed here so nothing is discovered halfway through phase 3.

The durable folder

The platform already teaches agents that agent-files/ survives across sessions and that agent-files/.tools/ is a hidden folder for the agent's own infrastructure, copied into place before each session. Apps follow the same shape: a hidden .apps/ for infrastructure, a visible apps/ only for apps that are meant to outlive a session.

Exploration: the agent keeps its own starters

Not a commitment. This section asks whether an agent can turn a custom app it built once into a starter it reuses, and whether user feedback on a starter can improve the next copy. Short answer: yes, with two existing mechanisms and one new operation.

The catalogue above is Agenta's. The gap it leaves is obvious the first time an agent builds something custom that the user likes: the next session starts from zero again. What the user means by "the agent learned to build X" is that the second session gets the same X, improved by whatever they said about the first.

Two facts that make it cheap

  • Every agent already has a cross-session folder. The runner mounts the agent's own drive into the sandbox as agent-files/, beside the session's files. Anything the agent writes there is visible to all of its later sessions and to its cron runs. It is exactly "the agent layout folder".
  • Skills carry files. A skill in the registry is a SKILL.md plus reference files, versioned as revisions, attachable to agents, with provenance and an update flow. A starter is a SKILL.md that says when to use it plus the app's files. The registry was built for "the agent learns a procedure"; an app starter is a procedure with files attached.

What promotion does

  1. Reads the instance's app.json to know which files are data and which are the app.
  2. Copies the app files, index.html, app.json, any inlined assets, and config.json as defaults, into the starter. Files listed under data are not copied. Session 1's retro items never appear in session 2.
  3. Writes the starter's SKILL.md: one paragraph on when to use it, taken from the conversation, plus the config keys. This is what lets the next session's "starter matches?" step find it.
  4. Versions it. A second promotion of the same slug becomes @2; instances record which version they came from, so "update this board to the latest" is a re-copy of non-data files.

Forking a platform starter is the same operation. "Our boards always need WIP limits" becomes an instance edit followed by promote, producing agent:board@1, which the skill prefers over platform:board@1 for this agent from then on.

Feedback as the learning signal

Two loops, both already visible in the figure. The instance loop: a user's change request lands in the instance and nowhere else, which is the safe default. The template loop: "make that the default" promotes the instance to the next version. The agent can also keep a NOTES.md in the starter and append a line when a user asks for the same change twice across sessions, so the next revision starts from evidence rather than memory. The registry's "used-by" list shows which apps came from which version, and the existing "update available" affordance is the natural way to offer @2 to an app still on @1.

If it is pursued, the cost is small. One platform operation, promote_app. A second source for create_app. One skill kind. Three lines in the agenta-apps skill: list agent starters first, propose promotion when an app settles, prefer revising over creating. It sits entirely on top of the phase 1 and 3 work above and changes nothing in the bridge.

Decisions

Is agenta-apps attached to every agent with a drive by default?
Yes, recommended. Detachable. Without it the feature is invisible to agents.
Starters as a platform op or as skill reference files?
Platform op. Deterministic bytes, no tokens, platform-stamped provenance.
Which starters ship first?
board only in phase 1. The other five after the first real apps, adjusted to what people actually ask for.
Manifest required for Run?
No. Any HTML file still runs. The manifest is what makes a folder an app in the UI and to the agent, not what unlocks execution.
Kit scope?
House style, under 6 KB. Tokens plus a dozen classes. Not a component library.
Starter updates?
Manual, later. The manifest records board@1; an "update available" affordance is a v2 that the field is ready for.
Should an agent be able to promote a custom app into its own starter?
Explore after phase 3. Skill-backed, user-initiated, data stripped. See the exploration section.
Can an agent put an app in the agent drive?
Not from the skill in v1. Session drive only. Cross-session apps are a later decision that carries the multi-user questions from the field test.
