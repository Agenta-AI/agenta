## Decisions I took (product-flavored), with options

### D1. A DM is one conversation (F88, F84)
- Today (JP's branch): each top-level DM message rooted its own thread; the agent forgot every
  message as soon as it answered; replies threaded under each message.
- Option A (taken): key the DM thread on the space; replies go top-level; `!new` starts a fresh
  session; the fill keeps what arrived since the current thread began.
- Option B: keep per-message threads in DMs and only fix the fill. Cheaper, but the QA called
  the result unusable and no Slack bot behaves that way.
- Side effect: a DM never "threads"; a user who wants a side thread in a DM gets a new
  top-level conversation instead. Acceptable for the first cut.

### D2. Default trigger set lives in the channel defaults
- The trigger vocabulary is {mention, command, action}. There is no "message" kind. A DM and a
  reply inside a held thread are admitted by the resolve step itself, not by a trigger kind.
- Option A (taken): channel defaults = all three; policy levels can narrow.
- Option B: add a "dm"/"thread" trigger kind. More knobs; nobody asked for them.

### D3. Slack read methods use query parameters (defect fix, not a product call)
- conversations.list/history/replies ignore a JSON body. Discovery pages to the end.

### D4. Reference key for a channel agent = workflow_variant, validated at write time
- The API refuses unknown keys and an empty map. The form keeps an existing agent's family on
  edit. A picker instead of a raw id input is deferred (UI lane).

### D5. Edit routes: omitted means unchanged (F91/F98)
- The service layers the sent fields over the stored row. `data` merges; there is no way to
  clear a data key by omission (send an explicit value instead). Flags merge field by field.

### D6. Delivery failure is written down (F87)
- FAILED with the platform's reason, then re-raise. ABANDONED is still never written (no retry
  budget exists in the worker today). Left for later.

## Live finding 2026-09-08 (afternoon): the approval CARD does not render on a park

What works: normal turns answer end-to-end on the Agenta channel (mock harness and Claude
haiku on the subscription login). The return path my lane built is unit- and
integration-tested: a click, a typed "Approve", or a numbered reply answers the parked
session interaction through the sessions respond path and opens no new turn.

What does not: when an `ask`-mode agent parks on a write, the runner parks correctly
(`park-approval tool=Write`, heartbeat running=false), but the channels outbox never renders
the approval card, so the user in the channel only ever sees "Working…". Cause: the channels
outbox folds and renders on a `turn_ended` event on `streams:sessions`; that event is
published only by `SessionTurnsService.complete_turn`, which a COMPLETED turn calls. A PARKED
turn never completes, so no `turn_ended` is published, the outbox never folds the paused turn,
and the card the render layer is ready to draw is never drawn. The orphan-sweep watchdog later
marks the parked turn "lost".

This is a sessions-streaming gap, not a channels one: the fix is to publish a park signal
(turn_ended with stop_reason=paused, or a dedicated turn_paused) to streams:sessions when a
turn parks on an interaction, so the channels outbox can render the card. It needs a
product/design call on the sessions side about where that signal is emitted. Recorded as a
blocker for the approval OUTBOUND path; the approval INBOUND path (answering) is done.

Decision for the first cut (superseded the same day, see the update below): Slack paste +
Agenta channel in THREAD scope, approvals deferred
until the park signal is wired. The `ask` mode is not refused at registration yet (documented
limitation on PR #6650).

  on a sessions-layer park signal. Decision
