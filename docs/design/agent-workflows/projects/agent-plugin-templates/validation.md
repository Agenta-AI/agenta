# Validation and acceptance

This document defines acceptance for the future package implementation and its integration with [PR #6395](https://github.com/Agenta-AI/agenta/pull/6395). PR #6944 is documentation only. None of the runtime scenarios below are reported as passed by this planning PR.

## Product outcome

A person can understand what a template will create, choose the accounts it will use, and reach a useful first run without asking a model to rebuild declared resources. They can leave and resume setup without losing their choices. They can distinguish “installed,” “needs setup,” and “ready,” and can tell which optional features they declined.

The proposed solution reuses the existing connection UI because it already exposes required needs and alternatives. Backend persistence addresses what UI reuse alone cannot prove: the selected account becomes the actual configuration, repeated requests create no duplicates, and readiness survives refresh. Validate both the user experience and these saved effects.

## Invariants and code-level checks

An invariant is a property that must hold across every entry point and retry, including direct API requests. Do not rely on disabled buttons or model instructions to enforce these properties.

| ID  | Invariant and responsible boundary                                                                                                                             | Required test                                                                                                                                                                                            |
| --- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| I01 | The loader validates the immutable snapshot before resource writes. Paths resolve inside allowed roots; unknown extension fields and dangling references fail. | Parser tests for traversal, symlink escape, duplicate keys, missing files, unsupported transports, and invalid entry/skill/agent references. Assert zero resource-service writes on rejection.           |
| I02 | The compiler is deterministic and has no network or storage side effects. Unbound slots never produce runtime entries.                                         | Compile the same snapshot and bindings twice and compare normalized native configurations. Validate the output with existing runtime schemas.                                                            |
| I03 | Slot identity includes installation, agent key, and connection key. Option identity is canonical within that slot.                                             | Round-trip adapter/API tests with duplicate provider names across agents, reordered options, and duplicate option rejection. Do not key bindings by labels or array offsets.                             |
| I04 | The backend validates project ownership, option membership, active account state, and secret-reference ownership before binding.                               | Negative API tests for another project, another installation, forged option, stale account, and unavailable secret. No configuration changes on rejection.                                               |
| I05 | Resource idempotency is scoped to project and request key. A key reused with a different snapshot or initial intent returns a conflict.                        | Concurrent database-backed requests, same-key retry, different-key install, and cross-project tests. Verify counts and resource identifiers.                                                             |
| I06 | A crash between a resource write and step acknowledgement cannot create duplicates on retry.                                                                   | Inject failure before and after each external service result, restart the worker, and reconcile using stable operation identity. If a service cannot support reconciliation, block rollout until it can. |
| I07 | All workflows exist before links compile. Package cycles are valid; synchronous execution cycles are rejected.                                                 | Shared-child and mutual-link fixtures; `A -> B` succeeds, `A -> B -> A` rejects before the second A starts, separate later `B -> A` succeeds, depth overflow rejects.                                    |
| I08 | Saved connection choice is authoritative; provider availability and display copy cannot replace it.                                                            | Select a non-primary account while both providers are active, compile, and inspect a safe tool dispatch. Test the same provider with two accounts.                                                       |
| I09 | Readiness is one server-owned predicate across completion, direct runs, subagent calls, and trigger dispatch.                                                  | Bypass the UI and attempt each path during installing/setup/failed/cancelled states. Only authorized setup and scoped verification may run; incomplete resources block completion.                       |
| I10 | No declared recipe activates without recorded approval through the trigger service.                                                                            | Install without a model and assert zero active triggers. Reject forged activation and reconcile an activation timeout.                                                                                   |
| I11 | Setup scope comes from the session's persisted installation and disappears after readiness/cancellation. Package guidance remains lower-trust content.         | Spoof client metadata and installation IDs; inspect the resolved context and exposed tools before/after completion. Instructions inside a package cannot widen setup authority.                          |
| I12 | Raw credential values never enter package bindings, revisions, transcript, logs, or traces.                                                                    | Use a synthetic secret marker and inspect captured outputs at each boundary; only secure credential storage may retain the value.                                                                        |
| I13 | Revision and file writes use expected revision/hash checks. Retry never overwrites an intervening user edit.                                                   | Concurrent-edit tests that return a conflict, preserve the user's content, and require re-read before retry.                                                                                             |
| I14 | Installation state and the greeting are durable independently of browser memory.                                                                               | Restart browser/API/worker at each handoff and assert one session and one greeting, including duplicate callbacks.                                                                                       |
| I15 | Permission policy remains enforced by existing runtime controls.                                                                                               | Execute representative read/write checks with native policy; connecting an account or editing setup prose cannot grant a write or bypass approval.                                                       |

Keep SQL and resource persistence in their owning services. Review imports and service calls to ensure frontend components do not call multiple resource-create endpoints, the compiler does not import provider clients, and the installation domain does not mutate another domain's tables. Cover these rules with existing dependency linting where available, otherwise include an explicit architecture review in the implementation PR.

Contract tests must validate the backend request/response models against the shared frontend client and slot adapter. Use a discriminated gateway/MCP union, closed payloads, reference-only credentials, and structured diagnostics. Reject client-authored `ready` state and arbitrary target resource IDs. These are interface requirements; finalize exact transport fields before implementation.

| Schema and compiler | Fixture names, commands, and results for I01-I03 and native-schema validation. Include the example package plus required-slot and multiple-account variants.                                    |
| Service and API     | Database-backed tests for authorization, concurrency, restart recovery, readiness, and approval. Resource counts and IDs must come from read-back, not mocks alone.                             |
| Frontend            | Shared adapter/card tests plus host-specific creation/handoff tests. Preserve existing connection-step regression tests.                                                                        |
| Browser             | A recording of applicable P01-P18 paths on the implementation commit, with desktop/mobile host and entry point named. Pair visible behavior with redacted installation/configuration read-back. |
| Product outcome     | A real first useful task after setup using the selected account. Separate model-output quality from deterministic installation checks.                                                          |

For each scenario record the commit SHA, environment, flags, fixture, result, evidence link, and any unresolved deviation. Mark unrun scenarios as not run. A mock UI, typecheck, or successful HTTP status alone cannot prove product acceptance. Do not describe the current docs-only PR as having passed these runtime checks.

## Validate that the solution fits the problem

Before expanding beyond one package, run a small moderated pilot with at least three intended users who did not write the implementation. Use the same concrete task on the legacy template path and the package path; alternate the order to reduce learning effects. This is qualitative evidence, not a statistically powered experiment.

Ask each participant to identify what will be created, select an alternative account, skip an optional feature, leave and resume, and produce a useful result. Record where they need help, misunderstand a label, or think an inactive automation is active. The proposed pilot acceptance gate is that all three complete these tasks without moderator intervention and correctly identify the selected account and automation state. If any fail, revise the flow and repeat the failed tasks before expanding the rollout.

Instrument installation start, connection resolution, resource completion, setup readiness, first useful run, retry, and abandonment with installation ID, package digest, host, and timestamps. Exclude credentials and transcript content. Compare completion rate, median setup duration, repeated questions, duplicate resources, and support errors with the legacy path on the same tasks. Do not claim an improvement without measured evidence or convert this small pilot into a percentage claim about all users.

## Release acceptance

The first package can leave its internal flag only when all applicable product scenarios and invariants pass on the implementation commit, the pilot gate passes, and no unresolved defect permits cross-project access, duplicate resources, incorrect account binding, lost resume state, or unapproved activation. Review actual resource read-back and the first useful result alongside recordings.

Keep broader rollout disabled if any gate fails. Account-provider equivalence, MCP support, and source import are accepted only for combinations actually tested. Repository/archive distribution has its own containment and source-parity checks in [the implementation plan](plan.md); it is not a prerequisite for the bundled-package pilot.
