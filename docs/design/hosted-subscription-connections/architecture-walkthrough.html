Hosting and deployment configuration

Where each kind of data lives

Existing vault

Keeps API keys and custom secrets. Native Codex and Grok login files bypass this store because the provider owns a changing set of files.

New authentication home

Keeps provider login files on encrypted persistent storage. Only a trusted login or run worker mounts it.

Agent workspace

Keeps conversation and session files. The authentication home path and contents never enter this workspace.

End-to-end sequence

The complete flow in six sentences

1. ChooseUser selects ChatGPT or SuperGrok.
2. CreateMain API creates a user-owned connection.
3. Sign inRunner starts the official provider login.
4. SaveProvider client writes private login files.
5. SelectAgenta picks the matching harness and model.
6. RunRunner mounts the same home and starts the agent.

Implementation gates

What must be proved before release

Tool isolation test

Codex or Grok must refresh its login. Shell and file tools started by the model must fail when they try to read the same files.

Stable SuperGrok login control

Grok documents device login, but its public docs do not describe a structured login API. The fallback is a pinned CLI version with a tested parser.

Recommended ownership

Only the user who connected the subscription can use it, and only from an interactive turn in the first release.

Recommended concurrency

Allow one active run per connection so two processes cannot refresh the same files together.

The service boundaries, ownership rule, storage operator, and release tests remain open decisions.
