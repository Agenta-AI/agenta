## 1. Verdict

The RFC gets the critical rows right. Stop is durable, direct, warm, and guarded. One execution
gets one terminal outcome. Every failure path ends in a session that accepts a new message. The
evidence from round two backs each of these. The design is not yet the smallest one that meets
those rows. It plans six milestones and five packages, where three would deliver the same user
value, and two of its contracts describe things the code base cannot do as written. The single
biggest change I would make is to the durable-history contract: session records live in the
analytics database and `session_streams` lives in the core database, so "lock the stream row,
insert the record, commit both together" is not one transaction. The per-session sequence must be
allocated inside the records database, or the records must move. That choice decides the shape of
snapshot, replay, retention, and the migration, so it comes before any producer work. Second to
that: the RFC should say that the first shipped increment is the Stop package behind one flag,
with the rest additive, and it should drop the new `POST /sessions/{id}/commands` Send path in
favor of the two routes that already exist.

## 3. Simplifications

- **Cut the generic commands route for Send.** Breaks nothing today. Queue and Steer get a route
  when they ship. Saves one admission path, one client migration, one idempotency store.
- **Cut the separate frame ingress and stream.** Reuse the records ingest stream with a temporary
  flag. Breaks nothing; the records worker already drops what it does not store. Saves a runner
  client, an API route, a Redis stream, and a second retention policy.
- **Cut the `execution.accepted` and `execution.waiting` events from the first vocabulary.** The
  approval path already parks the harness and starts a continuation under a new turn id. Add
  `waiting` with the approvals package. Breaks nothing until Queue and Steer.
- **Cut ownership talk from the RFC body.** The decision is "keep Redis ownership". One sentence
  and a pointer to `post-stop-liveness.md` is enough.
- **Merge "Shared client reader" into "Live relay".** A relay with no reducer has no user; a
  reducer with no relay has no data. One package, one flag, one QA gate. Breaks the plan's claim
  that the sender migrates later; keep that as the last step inside the one package.
- **Defer the snapshot route until the reducer exists.** The current transcript query plus the
  new sequence field on records is the snapshot for the first shared-reading increment.
- **Do not defer retention separation.** It is the one item that, if skipped, makes durable
  history a lie. It belongs to the first history increment.

| Order | Increment | Flag or guard | What ships | What the user gains |
|---|---|---|---|---|
| 1 | Records ack after commit (#6502) and admission before sandbox (#6500) | none, pure fixes | two small PRs on main | no lost records, no double-turn corruption |
| 2 | Stop and recovery (#6496, #6503, #6501, #6504) | `AGENTA_SESSIONS_DURABLE_STOP`, off in production for one release, on in every dev stack | durable Stop, direct delivery, warm continuation, watchdog settlement, late-output guard, runner owner release, Codex reap | Stop works in under a second and never kills the conversation |
| 3 | Durable history producer and retention | none needed; nullable columns, no client change | stable record ids, complete checkpoints, sequence allocation on the analytics engine, session retention exempt from tracing quota | history stops changing after commit and stops disappearing under quota |
| 4 | Shared reading | `AGENTA_SESSIONS_SHARED_READER`, honored by secondary readers only | temporary flag on ingest, relay consumer group, SSE fan-out, one reducer, snapshot | a second browser and mobile see live output |
| 5 | Sender on the shared path | same flag, sender opt-in | detach execution lifetime from invoke | refresh never stops a run |
| 6 | Queue, Steer, approvals over commands | a third flag | durable pending input | the queue is visible everywhere |

Increment 2 is where the big win sits. Everything after it is additive and can wait a release.

## 5. Questions for Mahmoud

1. **Where does the per-session sequence live?** Today session records are on the analytics
   engine and `session_streams` on the core engine. Option 1: allocate the sequence in the
   analytics database from a new small cursor table. One migration, no data move, retention stays
   with the rows. Option 2: move session records to the core database. A data move for every
   tenant, but one engine for all session state. Recommendation: Option 1. It is additive and
   reversible, and the move can happen later behind the same DAO.
2. **Reject or quarantine late output?** Option 1: reject with `execution_terminal`, no column,
   lose the late `usage` and tool result. Option 2: quarantine with the nullable column that
   exists, keep accounting, filter one predicate on reads. Recommendation: Option 2, because it
   is built, tested on the integrated stack, and deletes nothing.
3. **One Send route or two?** Option 1: keep invoke and add `on_busy` and an idempotency key to
   it. Option 2: add the generic commands route now. Recommendation: Option 1. The second route
   has no user value until Queue and Steer exist.
4. **Ship the Codex reap or bump the pin?** Option 1: ship the reap from #6496, which passed on
   the local provider and needs a `ps` check on the Daytona snapshot. Option 2: bump the Codex
   ACP pin from 1.1.7 to 1.8.0 and re-run the full Codex matrix. Recommendation: Option 1 for
   this release and Option 2 as a separate PR afterward, because the pin bump touches every
   Codex turn, not only Stop.
