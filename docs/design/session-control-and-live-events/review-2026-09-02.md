## Verdict in one paragraph

The RFC is accurate about the API and the records plane, and the direction is right. It is not
ready to implement as written in `tonight-handoff.md`, for one reason above all: the version-one
step list delivers Stop faster but never changes the runner park rule, so a faster Stop still
destroys the warm sandbox. Both reviewers found this independently. The fix is small and belongs
in version one. Three more holes need a rule each: Stop cannot reach a parked approval, a late
Stop kills the next turn, and a claimed command has no settlement owner when the runner dies.
With those four changes, the rest is ordinary work.

## What both reviewers agree on

1. **The park rule is the whole point of the Stop work.** `shouldPark` returns false whenever the
   abort signal is set (`services/runner/src/engines/sandbox_agent/engine.ts:26`), and the Stop
   path sets that signal (`services/runner/src/server.ts:519`). The turn already ends with
   `stopReason: "cancelled"` (`run-turn.ts:1188-1191`) but nothing reads it. A user Stop must
   park; other aborts keep destroying. Overnight action: Spike A builds this.
2. **A settlement watchdog is needed now, not after the spike.** Five "Stop and hung executions"
   issues only close with it. The Redis lease TTL is 3600 s, so it must key off heartbeat age
   (30 s interval, `contract.ts:18`), with a default of 90 s. Overnight action: the watchdog slice
   builds it.
3. **The double send needs no new table.** The atomic arbiter exists (`_start_turn`,
   `service.py:948-958`, mapped to 409 in the router) but the Send path never calls it, and the
   runner keepalive pool destroys the busy turn on its own (`session-coordinator.ts:1325`).
   `on_busy: reject` closes #6417, #5539, #5538 with a claim before start and the removal of the
   supersede branch. Queue and steer are product features on top. Overnight action: the admission
   slice builds it.
4. **Stop must cancel pending interactions.** Only kill does it today (`router.py:441-444`). The
   requirement has no owner in the RFC. Overnight action: the Stop guard slice builds it.
5. **The optional `expected_execution_id` is unguarded in practice** because the desktop sends
   none. First-party clients must always send it, and an absent id must not supersede a turn that
   started after the Stop was created. Overnight action: the Stop guard slice builds it.

## Where the reviewers differ

**Transport for Cancel.** The architecture reviewer keeps the RFC's long polling but requires the
poll loop to live for the session's warm lifetime, not the turn's, because the heartbeat stops
when a turn parks for approval (`server.ts:618`, `alive.ts:241-252`). The product reviewer says
long polling is not needed with one runner: the authenticated API-to-runner hop that kill already
uses (`runner_client.py:44`, runner `POST /kill` at `server.ts:704`) can carry `POST /cancel` today
and lands Stop in under a second. The RFC's own text allows both, because it puts the transport
behind a replaceable port and lists direct managed-runner routing as a later adapter.

Recommendation for the morning: keep the port from the RFC, build the direct-call adapter first
because it is one file and closes the latency bug now, and keep the long-poll adapter as the
second implementation when a parked-approval Stop or a second runner needs it. Spike B was told to
design the port so both adapters are one small file each, and to state what the durable command
record adds beyond the direct call (recovery when the runner is down, idempotency, audit).

**The durable command table.** The architecture reviewer keeps it. The product reviewer says a
lost Stop is not worth replaying because the user is still watching and pressing Stop again is
free; durability matters for Send and Steer, which version one does not do. Recommendation: build
the table only when the transport decision is made, and keep it out of the overnight code slices.
Nothing built tonight depends on it.

## Corrections to make in the RFC text

- `requirements.md` still lists ownership generations as a requirement; D-017 defers them. Mark
  the requirement deferred.
- `decisions.md` has two entries numbered O-009. Renumber.
- `rfc.md` never states the timing constants the design depends on: heartbeat 30 s, `alive` and
  `running` TTL 3600 s, tombstone TTL 3600 s refreshed on read, owner affinity 120 s, warm idle
  park window 60 s local and 120 s Daytona, approval park window 600 s. Add the table from the
  architecture review. The idle windows matter most: a warm Stop gives the user one to two minutes
  to resume before the sandbox is reclaimed. The reviewer recommends the 600 s approval window
  for a stopped session.
- `research.md` calls the vendored cancel guard "not yet verified". It is verified and client-side:
  `chunk-TVCDKGSM.js:1550-1551` throws unless `allowManagedCancel`, and only `destroySession`
  passes it. Spike A confirms whether the daemon inside the sandbox also needs a change.
- Closing a chat tab sends the same cancel as the Stop button
  (`AgentChatPanel.tsx:133-139`), which contradicts the requirement that sender disconnection
  does not stop execution. Name it as a deliberate rule or remove it.
- The interface shapes: use `policy: {on_busy}` and `input: {text, attachments}` in the command
  body; keep `expected_execution_id` under `target`; drop `position` from pending inputs; add a
  `continuation.status` to the interaction response body. Details in the architecture review,
  section 4.
